Project showcase

A gesture classifier built
around its hardware

This project trains spiking neural networks to recognise hand gestures from an event camera, and targets a neuromorphic chip called HiAER-Spike. The chip constrains how a network may be wired and what precision its numbers may carry. Those constraints drive every decision in the code, so this walkthrough starts with the hardware and works outward from it.

1.1The hardware: HiAER-Spike

HiAER-Spike is a neuromorphic research platform developed at UC San Diego and programmed through a Python interface called hs_api. It executes networks of spiking neurons directly. A neuron on the chip holds a small amount of state, receives events from other neurons, and emits an event of its own when its state crosses a threshold. It is a binary framework.

The appeal is power consumption. A conventional processor evaluates every unit of a network on every input. This chip performs work only where an event actually arrives, so a workload with little activity costs little energy.

In exchange, the chip fixes several properties of any network it runs. These are hardware facts, not settings, and the rest of this project exists to work inside them.

neuron update orderfixed The neuron fires on the state it carried in from the previous timestep, then resets, leaks, and integrates. Each layer therefore delays its output by one timestep.

Two of these have consequences that reach far into the code. Because thresholds and weights are quantised, a network measured in floating point is not the network that runs. Because the update order is fixed, a network trained with a different order produces different spike times once converted.

1.2Conventional neural networks

Most neural networks in use today are artificial neural networks, or ANNs. A unit in an ANN computes a weighted sum of its inputs, applies a nonlinear function, and passes the resulting number forward. Values are continuous, typically 32-bit floating point, and every unit evaluates on every input.

A convolutional NN applies the same small filter across an image and stacks layers of these filters. The design is a good match for a GPU, which multiplies large dense matrices quickly. HiAER-Spike does not run this model of computation, because there spikes are binary and only store 0s/1s and due to their nature of only firing when necessary, dense multiplication is inefficient and undesireable.

1.3Spiking neural networks

A spiking neural network, or SNN, replaces the continuous activation with a binary event. Each neuron keeps one number, the membrane potential v, and updates it over a sequence of timesteps.

  • Incoming spikes add their connection weights to v. Negative weights subtract.
  • Between updates v decays toward rest at a rate set by a constant τ. Older input therefore counts for less than recent input. v/τ is used as a leaky term so that larger τ's reflect a longer memory
  • When v crosses a threshold θ, the neuron emits a spike and v returns to zero.

This neuron model is called leaky integrate-and-fire, abbreviated LIF, and it is the model HiAER-Spike implements. Its parameters are the leak τ, the threshold θ, and the reset value.

The order of those operations is fixed by the hardware, as listed in section 1.1, and it affects when spikes appear. At each timestep the neuron first compares the potential it carried in from the previous timestep against θ, then resets if it fired, then leaks, and only then adds the current input. Input arriving at timestep t therefore cannot produce an output spike before timestep t+1.

Because a single spike carries almost no information, an SNN is run for T timesteps and its answer is read from how often each output neuron fired. The simulator below runs the same update rule the chip uses.

1.4Why the two models differ in cost

The distinction that matters for hardware is when work happens. An ANN unit multiplies each of its inputs on every evaluation. An SNN neuron does arithmetic only for inputs that spiked, and a spike contributes an addition rather than a multiplication.

1.5The workload: DVS128 Gesture

The dataset is DVS128 Gesture, published by IBM in 2017. It contains recordings of 29 people performing 11 gestures, including hand waves, arm rotations, air drums and air guitar, under three lighting conditions.

The recordings come from a dynamic vision sensor, an event camera with a 128×128 array. A conventional camera reports the brightness of every pixel at a fixed frame rate. Each pixel of an event camera instead reports independently, and only when its own brightness changes. A report of an increase and a report of a decrease occupy separate channels, which is why the data has two channels rather than three.

A still background produces no events. A moving hand produces a dense stream of them along its edges. The recording is therefore a sparse sequence of changes, which matches what a spiking network consumes.

The code converts each recording into T frames by dividing the event stream into T groups of equal event count and rasterising each group.

1.6What the project sets out to do

A network for this chip has many free parameters: how many convolution layers, how wide, what kernel size, how the resolution is reduced, how many timesteps, what leak and threshold the neurons use, and how the network is trained. Some combinations exceed the routing limits in section 1.1 and cannot be built. Others fit but lose accuracy when their weights are quantised.

The project searches that space automatically. The requirement is a configuration that satisfies the hardware limits and reaches at least 97.5% validation accuracy, measured on the converted network rather than on the floating-point one.

Observation

A network trained in floating point differs from the network the chip runs in weight precision, threshold precision, leak resolution, neuron update order, and the presence of batch normalisation. Each difference changes the output, and none of them appear in a training accuracy figure.

Consequence

Accuracy measured during ordinary training overstates what the deployed network achieves, so it is the wrong quantity to optimise. Any search guided by it will prefer configurations that happen to degrade badly on conversion.

In code

Each trial ends by converting its network into the deployable form and evaluating that instead. The resulting hw_val_accuracy is the value the search optimises. A configuration that cannot be represented on the chip scores zero, whatever it reached during training.

1.7How the code is organised

The implementation is a single file, Practice2.py, divided into numbered sections. Sections 1 to 4 import no deep learning libraries, so architecture planning and the feasibility check run on any machine without a GPU stack installed.

The diagram below maps those sections onto the four jobs the file performs. Each leaf links to the page that covers it.

Running it

terminalfour modes
python Practice2.py summary --input resize_to=64 T=16 --encoder depth=2 channels=32 kernel_size=7
python Practice2.py single  --data-dir <DVS128 root> --ckpt best.pth
python Practice2.py fold    --ckpt best.pth --data-dir <DVS128 root>
python Practice2.py search  --compute local --trials 50 --data-dir <DVS128 root>
  • summary prints the architecture table, the neuron and synapse counts, and the feasibility verdict. It needs no GPU.
  • single trains one configuration and reports both its float accuracy and its converted accuracy.
  • fold loads a checkpoint, folds batch normalisation into the convolutions, quantises, verifies the result, and writes the per-layer tables the converter reads.
  • search runs the automated search.
