Project showcase

A configurable SNN built for HiAER-Spike

This project is a Python program that finds the best performing configuration of a user-specificed spiking neural network under the constraints of HiAER-Spike, a neuromorphic platform. The platform limits how a network may be wired, supports only a narrow set of operations, and works in limited precision. These constraints drastically alter how a network is constructed, trained, and evaluated. The program is built for reuse. The network and the hardware limits are both supplied as configuration, so the user can point it at a new architecture, or raise the limits as HiAER-Spike develops, without rewriting the search. The immediate goal is to find parameters that increase accuracy for a specified network while the long-term goal is an analysis of which parameters are worth focusing on and expanding capabilities in.

1.1Introduction to HiAER-Spike

HiAER-Spike is a neuromorphic research platform developed at UC San Diego and programmed through a Python interface called hs_api. It executes networks of spiking neurons directly. A neuron on the chip holds a small state, receives events from other neurons, and emits an event of its own when its state crosses a threshold. These events carry information solely through their spikes; a neuron does/doesn't fire.

The appeal of such a framework is power consumption. A conventional GPU evaluates every unit of a network on every input. This platform performs work only where an event actually arrives, so a workload with little activity costs little energy.

1.2Conversion from a trained model to hardware-executable one

A network is trained in PyTorch, where a layer is a compact object and every number is a 32-bit float. The platform has neither of these capabilities. This is the job of a converter, supplied as part of hs_api.

Observation

The platform defines networks in terms of indvidual neurons, int16 values, and messages passing between neuron. There are no broader categories such as fully connected and convolutional layers.

Consequence

Every layer must be expanded into the individual neurons it implies and every connection between them has to be listed explicitly. Additionally, every floating-point number must be mapped onto an int-16.

In code

The converter performs this expansion. However, more relevant to us, our snnsearch/quantgrid.py mirrors its arithmetic exactly, so that a network is trained against the numbers the converter will produce rather than adjusted to them afterwards. This prevents massive losses in accuracy due to conversion and discourages dependence on high-precision weight values for storing information.

Expansion by the Converter

The platform holds a table that maps which neuron sends to which other neuron, and with what weight. The converter walks each layer and writes out one neuron for every output position in every channel, then lists that neuron's incoming connections one by one. A single convolution of 32 channels over a 29×29 image with a 7×7 filter becomes 4,608 neurons holding 7.2 million connections between them, from 50,176 trained numbers.

Four terms follow from that picture, and they appear throughout this project.

synapse
One connection between two neurons, holding one weight.
axon
An input line carrying spikes into the chip from outside. For our example, a DVS camera feeds these.
fan-in
How many connections arrive at one neuron.
fan-out
How many connections leave one neuron toward the next layer.

Each of the last three has limit on how large they can be, because each one counts rows in the platform's routing table, and that table is a fixed size. These connection/routing limits directly determine whether or a not a network can be constructed.

Mapping floating-point onto int16

The platform's memory holds 16-bit signed integers, so the values that exist on it discretely range from −32767 to +32767. Weights can possess values awkward values such as 0.7, which needs to be represented by one of such integer values. To do this, the converter defines w_alpha and fixes it at 1. The constant dictates that the largest integer (+32767) represents the value 1.0.

This brings up the issue of weights beyond 1.0, such as 1.3 which has no integer available to it. The converter replaces it with 1.0. Truncation loses information and must be accounted for. Within the range [-1,1], the spacing between neighboring integers is about 0.00003, so snapping to the nearest available integer has negligible loss of information.

Firing thresholds and the decay constant are mapped the same way.

Running it

Once the network is expanded and mapped, the converter feeds the input as spikes for T timesteps, runs a few further timesteps with no input at all, and counts the spikes each output neuron produced. The extra timesteps are there because each layer holds its output back by one step, so the last frame of input needs a moment to reach the far end. Those trailing timesteps are called the flush. The reason behind flushing will be discussed later.

1.3Platform Limits

The routing table of fixed size and an int16 number format produce the following hardware limits.

ConstraintValueRestriction
input axons16,383 Total input lines into the chip. An input image larger than this cannot be presented at all.
neuron fan-in8,159 How many sources one neuron may listen to. Caps how large a window one convolution neuron may read, and the width of a fully connected layer.
neuron fan-out4,095 How many destinations one neuron may drive.
weight formatINT16, |w| ≤ 1 Weights are 16-bit integers on a fixed grid of 1/32767. Values outside the range are truncated rather than rescaled.
threshold formatint(θ · 32767) Firing thresholds, as mentioned earlier, have the same int16 limits. θ must stay within (0, 1].
leakINT16 The decay constant of a neuron snaps to the nearest integer, which is extremely detrimental to accuracy. While developing this program, statistical analysis showed that tau had the greatest effect on the accuracy during floating-point training.
available layersconv, linear, pool (restricted) No bias terms are allowed, as the platform only supports multiply-adds with weights and the routing table stores no bias. There is also no batch normalization, which is a layer that rescales each channel using statistics gathered during training.
neuron update orderN/A The neuron fires on the state it carried in from the previous timestep, resets, leaks, and integrates. Each layer therefore delays its output by one timestep.

Quantizing to int16 and the methodology of update order heavily impact the network and should be paid attention to.

1.4Conventional neural networks

Most neural networks in use today are artificial neural networks, or ANNs. A unit in an ANN computes a weighted sum of its inputs, applies a nonlinear function, and passes the resulting number forward. Values are continuous, typically 32-bit floating point, and every unit evaluates on every input.

A convolutional NN applies the same small filter across an image and stacks layers of these filters. The design suits a GPU, which multiplies large dense matrices quickly. HiAER-Spike cannot run it. Its neurons exchange binary events rather than continuous values, and they do work only where an event arrives, so there is no dense matrix for the hardware to multiply.

1.5Spiking neural networks

A spiking neural network, or SNN, replaces the continuous activation with a binary event. Each neuron keeps one number, the membrane potential v, and updates it over a sequence of timesteps.

  • Incoming spikes add their connection weights to v. Negative weights subtract.
  • Between updates v decays toward rest at a rate set by a constant τ. The amount removed each step is v/τ, so a larger τ leaks less and carries evidence for longer. Older input counts for less than recent input.
  • When v crosses a threshold θ, the neuron emits a spike and v returns to zero.

This neuron model is called leaky integrate-and-fire, abbreviated LIF, and it is the model HiAER-Spike implements. Its parameters are the leak τ, the threshold θ, and the reset value.

The order of those operations is fixed by the hardware, as listed in section 1.3, and it affects when spikes appear. At each timestep the neuron first compares the potential it carried in from the previous timestep against θ, then resets if it fired, then leaks, and only then adds the current input. Input arriving at timestep t therefore cannot produce an output spike before timestep t+1.

Because a single spike carries almost no information, an SNN is run for T timesteps and its answer is read from how often each output neuron fired. The simulator below runs the same update rule the chip uses.

1.6Why the two models differ in cost

The distinction that matters for hardware is when work happens. An ANN unit multiplies each of its inputs on every evaluation. An SNN neuron does arithmetic only for inputs that spiked, and a spike contributes an addition rather than a multiplication.

Event camera recordings are mostly silent, so this difference is large in practice. The comparison below runs one neuron with six inputs for sixteen timesteps and counts the operations each model performs.

1.7The workload: DVS128 Gesture

The dataset is DVS128 Gesture, published by IBM in 2017. It contains recordings of 29 people performing 11 gestures, including hand waves, arm rotations, air drums and air guitar, under three lighting conditions.

The recordings come from a dynamic vision sensor, an event camera with a 128×128 array. A conventional camera reports every pixel's brightness on a fixed clock. An event camera has no clock. Each pixel reports on its own, only when its own brightness changes, with increases and decreases arriving on separate channels. That last detail is why the data has two channels rather than three.

A still background produces no events at all, while a moving hand throws off a dense stream of them along its edges. What the sensor records is a sparse sequence of changes, which is the kind of input a spiking network consumes.

The code converts each recording into T frames by dividing the event stream into T groups of equal event count, then turning each group into an image by counting the events that landed on each pixel.

1.8What the project sets out to do

A network for this chip has many free parameters: how many convolution layers, how wide, what kernel size, how the resolution is reduced, how many timesteps, what leak and threshold the neurons use, and how the network is trained. Some combinations exceed the connection limits in section 1.3 and cannot be built. Others fit but lose accuracy when their weights are quantized.

The project searches that space automatically. The requirement is a configuration that satisfies the hardware limits and reaches at least 97.5% validation accuracy, measured on the converted network rather than on the floating-point one.

Observation

A network trained in floating point differs from the network the chip runs in weight precision, threshold precision, leak resolution, neuron update order, and the presence of batch normalization. Each difference changes the output, and none of them appear in a training accuracy figure.

Consequence

Accuracy measured during ordinary training overstates what the deployed network achieves, so it is the wrong quantity to optimize. Any search guided by it will prefer configurations that happen to degrade badly on conversion.

In code

Each trial ends by converting its network into the deployable form and evaluating that instead. The resulting hw_val_accuracy is the value the search optimizes. A configuration that cannot be represented on the chip scores zero, whatever it reached during training.

1.9How the code is organized

The implementation is a Python package, snnsearch, with one launcher beside it. Modules are layered so the cheap parts stay cheap: the four that describe and check a configuration import no deep learning library at all, so planning and the connection check run on a laptop with nothing installed.

The diagram below maps the modules onto the four jobs the package performs. Each leaf links to the page that covers it.

Running it

A run is described by a configuration file and started by one command. Flags override the file, so a saved config stays the record of intent while a flag varies one thing.

terminalfive modes
python main.py check                              # what this machine is missing
python main.py summary -c configs/dvs128.yaml     # no torch, no dataset needed
python main.py single  -c configs/dvs128.yaml     # train one configuration
python main.py search  -c configs/cifar10.yaml    # the automated search
python main.py report  results/dvs128             # rebuild report.html
  • check reports which packages, which GPU and which dataset files are present, and what each missing one blocks.
  • summary prints the architecture table, the counts and the feasibility verdict. It imports no deep learning library, so it is the cheapest way to confirm an install works.
  • single trains one configuration, folds it, quantizes it and reports both accuracies with the gap between them.
  • search runs the automated search and writes results as it goes.
  • report rebuilds the HTML report from a finished run directory.

What a configuration file holds

Values live in the file. A dataset is code rather than values, so the file points at a Python callable for that and carries everything else.

configs/dvs128.yamlabridged
dataset:
  name: dvs128                 # or module: examples/my_data.py
  root: /local_disk/$USER/DVS128Gesture

encoding:
  coding: passthrough          # already events; resize and binarize only
  T: 16
  resize_to: 64                # native 128x128 needs 32,768 axons, limit is 16,383

search:
  trials: 25
  epochs: 40
  gpu_fraction: 0.25           # the model needs ~250 MB, so four trials share a card

objective:
  mode: accuracy               # accuracy | constrained | weighted | pareto

The format is YAML rather than JSON because every narrowed range in this project carries the statistic that narrowed it, on the same line. JSON has no comments, so it would strip exactly the property that makes the search space checkable.
