The search

The search proposes configurations, rejects those that exceed hardware limits, and trains the remaining candidates. Early validation scores control stopping, while accuracy after conversion determines the final ranking.

6.1The components

A trial is one experiment with one chosen configuration. Hyperparameters are choices made before fitting the weights, such as layer width or learning rate. A search repeats trials to find settings that perform well under a fixed evaluation procedure.

Choosing settings · Optuna
A library for proposing hyperparameters. Here it uses completed trials to guide later proposals. It does not implement the neuron, hardware checks, or training loop.
Running experiments · Ray Tune
A library that schedules trials on the available CPUs and GPUs, collects reports, and saves search state. The resource allocation is configurable. It can manage experiments on one machine or a cluster.
Allocating training time · ASHA
Asynchronous successive halving is an early-stopping method provided by Ray Tune. It compares scores at scheduled checkpoints and stops weaker trials, allowing other trials to use the resources. A trial that improves late can be stopped too soon.

The project-specific work connects these tools to the same model planner, hardware checks, training procedure, and converted-model evaluation. Ray's concepts guide distinguishes trial management from proposal and stopping algorithms; Optuna supplies the proposal library.

The search also begins from three known configurations rather than from nothing. Their geometry, two or three layers of 32 channels with kernel 5 or 7 at 64×64 input, came from an earlier study. The comment attached to them notes that their recorded accuracies were measured under the older floating-point objective and will not reproduce, so they serve as starting points for the sampler rather than as claims.

6.2Three tiers of evaluation

Implementation details

Connection checks can reject a configuration before training. Among configurations that fit, intermediate validation scores identify candidates for early stopping.

A trial first passes the hardware checks. It then trains until the epoch budget is exhausted or ASHA stops it. Completed trials are converted and evaluated for the final ranking.

trainable(config) runs three tiers: the feasibility check, then floating-point training that reports each epoch, then the conversion and its measurement. An infeasible configuration reports a score of zero and returns before any GPU work.

  1. Feasibility, microseconds The check from section 4.1. Earlier versions raised an exception when a feature map collapsed; the planner now returns that as data, so the trial records a score instead of crashing.
  2. Training, minutes to hours The schedule from section 5.6, reporting validation accuracy every epoch. These reports exist to support early stopping and are not the objective.
  3. Conversion, one measurement Fold, quantize, export and evaluate. A configuration that deployment_report marks undeployable scores zero regardless of its training accuracy.

6.3Two metrics with different jobs

The question during training is whether a candidate should receive more time. The question at the end is how well its transformed network performs. These need separate scores.

float_val_accuracy
The intermediate validation score reported during training and read by ASHA. The historical field name can also cover training phases that simulate quantization; it does not guarantee an entirely floating-point forward pass.
hw_val_accuracy
Validation accuracy from software evaluation of the transformed model. The “hw” prefix does not mean that this measurement came from a physical chip.
val_accuracy
The final search objective sent to Optuna. It uses the transformed validation score when the candidate passes deployment checks and zero when the candidate is rejected.
Which score each component reads

Early stopping needs a score at regular training intervals. Final selection needs a score after export. Reporting these separately prevents training progress from being confused with conversion effects.

The early-stopping scheduler reads intermediate validation scores. The sampler reads each completed trial’s final converted score. Separate metric keys prevent these two measurements from being mixed.

ASHA prunes on float_val_accuracy, reported each epoch. Optuna selects on val_accuracy with scope="last", and the last report of every trial carries the converted figure. Ray's shared configuration is left without a metric, because the searcher and the scheduler deliberately use different ones.

Follow one trial through both score streams

During training, each epoch reports validation accuracy under float_val_accuracy. ASHA uses these intermediate reports to decide whether the trial receives more training time. A trial stopped at this stage has no final converted score.

A completed trial exports its network and evaluates it again. That final value is reported under val_accuracy. Optuna uses the last report to rank the completed configuration and propose later trials.

Keeping the keys separate prevents an early training score from being mistaken for the converted result. A hardware-infeasible configuration is rejected before training. A pruned trial is recorded as stopped, which preserves the distinction between missing final evaluation and measured low accuracy.

6.4Early stopping

An epoch is one pass through the training data. The grace_period gives a feasible trial an initial training budget before score-based stopping. The reduction_factor controls how aggressively trials are eliminated. With a grace period of 8 and a reduction factor of 3, comparisons occur around 8, 24, and 72 training reports, within the configured budget. Roughly the strongest third continue at each comparison. Trials arrive asynchronously, so this is not a fixed tournament with all candidates evaluated together.

The grace period is kept above one for two reasons recorded in the comments. Section 5.5 noted that cosine and onecycle schedules improve late, so judging too early favors configurations with a flat learning rate. Infeasible trials also report once at epoch zero, and a grace period above one keeps them from forming a checkpoint and lowering the bar for everything else.

6.5A conditional search space

Sampling only the applicable settings

Some parameters exist only for some configurations. A four-layer network has a kernel size for its fourth layer; a two-layer network does not. A flat parameter dictionary would supply a value for that parameter on every trial, including those where it had no effect.

Sampling a fourth-layer setting for a two-layer network would add a parameter that cannot affect the result. Conditional sampling avoids these unused settings.

The space is a function executed per trial, calling trial.suggest_* only for parameters that apply. It is defined as DefineByRunSpace, a class rather than a nested function, because Ray checkpoints the sampler by pickling it and a nested function cannot be pickled. The file pickles the space once at startup to verify this before any GPU time is spent.

6.6What the first study changed

The sampled ranges were narrowed using results from an earlier 65-trial study, and each narrowing carries its evidence in a comment.

Two ranges were reopened because their earlier measurements used floating-point settings or objectives that did not match the deployed model. Those measurements need reevaluation under the current procedure.

6.7Recording results as they happen

Writing partial search results

The project’s consolidated export runs after the search returns. Incremental project reports also preserve results when a run is interrupted. Ray’s own trial logs and checkpoints are separate artifacts.

The driver writes results as they arrive. Keeping shared-file writes in one process prevents concurrent trials from interleaving their output.

ResultsWriter appends one line per record and calls fsync, so the file can be followed live. Multi-line files are written to a temporary name and renamed atomically. All writing happens in a single callback in the driver process.
