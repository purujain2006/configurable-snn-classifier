The search

Pages 2 to 5 built one configurable network and a way to measure what it achieves after conversion. This page covers the process that searches the configuration space on a fixed hardware budget, and the metric that decides which configuration wins.

6.1The components

Three libraries divide the work, and the file wires them together with settings that matter enough to be defended in comments.

Optuna
Proposes configurations. It models the relationship between past configurations and their scores, and samples new ones in promising regions while continuing to explore.
Ray Tune
Runs each proposed configuration as a separate process with one CPU and one GPU, collects the metrics each trial reports, and checkpoints the search itself. It runs on one machine or across a cluster.
ASHA
Stops trials whose accuracy curve falls behind at fixed checkpoints, which frees hardware for new proposals.

The search also begins from three known configurations rather than from nothing. Their geometry, two or three layers of 32 channels with kernel 5 or 7 at 64×64 input, came from an earlier study. The comment attached to them notes that their recorded accuracies were measured under the older floating-point objective and will not reproduce, so they serve as starting points for the sampler rather than as claims.

6.2Three tiers of evaluation

Observation

Configurations differ enormously in how much they cost to evaluate. Section 4.1 showed that a large fraction violate the routing limits, which arithmetic detects in microseconds. Among the rest, many are clearly weak within a few epochs.

Consequence

Spending equal time on every proposal wastes most of the budget. Evaluation should proceed in stages, with each stage cheap enough to justify the population that reaches it.

In code

trainable(config) runs three tiers: the feasibility check, then floating-point training that reports each epoch, then the conversion and its measurement. An infeasible configuration reports a score of zero and returns before any GPU work.

  1. Feasibility, microseconds The check from section 4.1. Earlier versions raised an exception when a feature map collapsed; the planner now returns that as data, so the trial records a score instead of crashing.
  2. Training, minutes to hours The schedule from section 5.6, reporting validation accuracy every epoch. These reports exist to support early stopping and are not the objective.
  3. Conversion, one measurement Fold, quantize, export and evaluate. A configuration that deployment_report marks undeployable scores zero regardless of its training accuracy.

6.3Two metrics with different jobs

Observation

Early stopping needs a value reported every epoch, which only floating-point training provides. Selection needs the converted accuracy, which exists once per trial. A single metric cannot serve both without comparing quantities that are not alike.

Consequence

The two roles need separate keys, and the scheduler and the sampler must be pointed at different ones. The final report of a trial has to be the converted measurement, so that a sampler reading the last report reads the right number.

In code

ASHA prunes on float_val_accuracy, reported each epoch. Optuna selects on val_accuracy with scope="last", and the last report of every trial carries the converted figure. Ray's shared configuration is left without a metric, because the searcher and the scheduler deliberately use different ones.

A failure this wiring caused

ASHA stops a trial once it has reported max_t times, and every report counts. The conversion result is one extra report after the final epoch. With max_t = epochs the trial was stopped on its last epoch and that extra report never arrived, so hw_val_accuracy was missing for every trial and selection fell back to floating-point accuracy. Nothing failed visibly. The setting is now max_t = epochs + 1.

6.4Early stopping

Every trial is guaranteed grace_period epochs, eight by default. After that, at checkpoints placed at grace × rfk epochs, a trial continues only if it ranks in the top 1/rf of the trials that reached the same checkpoint.

The grace period is kept above one for two reasons recorded in the comments. Section 5.5 noted that cosine and onecycle schedules improve late, so judging too early favors configurations with a flat learning rate. Infeasible trials also report once at epoch zero, and a grace period above one keeps them from forming a checkpoint and lowering the bar for everything else.

6.5A conditional search space

Observation

Some parameters exist only for some configurations. A four-layer network has a kernel size for its fourth layer; a two-layer network does not. A flat parameter dictionary would supply a value for that parameter on every trial, including those where it had no effect.

Consequence

The sampler would then model a relationship between a parameter and a score in trials where the parameter did nothing, which corrupts its estimate. Parameters need to be sampled only along the path a trial actually takes.

In code

The space is a function executed per trial, calling trial.suggest_* only for parameters that apply. It is defined as DefineByRunSpace, a class rather than a nested function, because Ray checkpoints the sampler by pickling it and a nested function cannot be pickled. The file pickles the space once at startup to verify this before any GPU time is spent.

6.6What the first study changed

The sampled ranges were narrowed using results from an earlier 65-trial study, and each narrowing carries its evidence in a comment.

ParameterNowReason recorded in the file
channels32, 64Wider layers drove infeasibility (chi-square p=6e-4, Cramér's V=0.59) and never scored better.
kernel5, 7Every configuration in the top ten used one of these.
depth2 to 4Shallow networks were favored (Kruskal-Wallis q=0.08). Depth 5 never exceeded 0.77.
hidden layers0 or 1Every configuration in the top ten used none (q=0.04).
normalizationbn, tdbnRemoving normalization produced every network that failed to learn (p=0.0015).
resize_to32, 64Native resolution needs 32,768 axons against a limit of 16,383, so it can never pass.
learning rate5e-4 to 5e-3Positive correlation with accuracy (Spearman q=0.04); the lower end under-converged.
τreopenedThe previous result described continuous values that all deploy as the same integer, so it does not transfer.
weight decayfloors raisedFitted under an objective that could not observe weight clipping, which section 4.3 showed it controls.

Two of these entries are reopenings rather than narrowings. A result that describes a coordinate the hardware cannot represent, or that was measured under an objective now known to be wrong, carries no information about the current objective.

6.7Recording results as they happen

Observation

Ray writes its consolidated export after the search returns. A search that runs for thirty hours and is then interrupted leaves nothing behind.

Consequence

Results have to reach disk as they are produced, in a form that stays valid between writes. Trials run in separate processes, so writing from inside a trial would interleave output from several at once.

In code

ResultsWriter appends one line per record and calls fsync, so the file can be followed live. Multi-line files are written to a temporary name and renamed atomically. All writing happens in a single callback in the driver process.
