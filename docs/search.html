The search

A search tries hundreds of network configurations on a fixed compute budget. This page covers the tools it uses, how it avoids spending GPU time on networks that cannot run or cannot win, what it samples, and what it writes down.

6.1The parts

Each trial trains and scores one configuration. A hyperparameter is a choice made before training, such as a layer's width or the learning rate (how large each training update is). Searching means running many trials to find hyperparameters that score well.

Optuna
Proposes the next configuration to try. It looks at the scores of finished trials and proposes values near the good ones more often.
Ray Tune
Runs many trials at once across the available GPUs, collects their reports and saves the search's progress. See Ray's concepts guide.
ASHA
An early-stopping rule that comes with Ray Tune. It compares trials at set points in training and stops the weaker ones, so their GPU time goes to better ones.

This project's part is connecting those tools to its own planner, chip check, training procedure and simulator check.

6.2Four stages per trial

Each stage is far more expensive than the one before, so cheap stages run first and stop a trial as early as possible.

  1. Chip check, microseconds. The connection limits from section 4.1. A network that cannot fit scores zero and never reaches a GPU.
  2. Training, minutes to hours. The schedule from section 5.6, reporting validation accuracy every epoch so ASHA can stop weak trials.
  3. Export, one evaluation. Fold, round and score the deployable network. A network with an illegal threshold scores zero.
  4. Simulator check, seconds. The validation clips run through IntegerSim. A network the simulator cannot run is marked not deployable.

6.3Different scores for different jobs

During training, the question is whether a trial deserves more time. At the end, the question is how well its deployable network does. These need separate scores.

float_val_accuracy
Validation accuracy reported every epoch during training. ASHA reads this to decide which trials to stop.
val_accuracy
The score Optuna optimizes: the deployable network's validation accuracy, or zero if the network cannot be deployed.
sim_val_accuracy, sim_disagreements
The simulator's accuracy on the same clips, and how many clips it classifies differently from PyTorch.

Keeping these apart means a good training curve is never mistaken for a good deployed network, and a trial that ASHA stopped is recorded as stopped instead of as a score of zero.

6.4Early stopping

ASHA lets every trial train for a grace period, then compares it with the others at checkpoints spaced by a reduction factor. With a grace period of 20 epochs and a factor of 3, as in the current DVS128 configuration, the checkpoints fall at 20 and 60 epochs of an 80-epoch budget, and roughly the best third of trials continue past each one. The configuration also uses two brackets: half the trials are not judged until epoch 60, which protects networks that start slowly. Trials start and finish at different times, so each is compared with whichever trials have reached the same checkpoint.

Some learning-rate schedules improve most toward the end of training, so a grace period that is too short stops promising trials early. The demo shows the effect: set the grace period to 1 and the late-improving curves are cut.

6.5Sampling only what applies

Some settings exist only for some networks. A four-layer network has a kernel size for its fourth layer, and a two-layer network does not. Optuna's "define-by-run" mode builds each trial's settings step by step, so a trial only has the settings it actually used.

The order of those steps matters. The search samples the network's shape first, checks it against the chip, and only then samples training settings such as the learning rate. Previously, a shape that failed the chip check scored zero together with training settings it never used, so Optuna learned that those training settings were bad. Sampling the shape first and stopping there on failure means a rejected network only counts against its shape.

A balanced start

Optuna favors whatever has scored well so far, so an option that starts badly can end up barely tried. In an earlier 400-trial search, 32 trials used GAP and 26 used the firing-rate penalty, too few to judge either. The search therefore begins with a balanced block covering ten choices: pooling (none, average, max), bias (threshold, bias neurons), head (flatten, GAP), signed spikes, bits per pixel (one, more), τ (fixed, per layer, per channel), loss (rate, TET), augmentation, convolution dropout and the firing-rate penalty. Every combination of all ten would take 2,304 trials. Instead, each option appears equally often across the block, and every pair of choices is spread as evenly as possible, so no option is mostly tried alongside one setting of another. Each trial in the block gets a random network shape that fits the chip, and Optuna samples the rest. tools/analysis/factor_effects.py compares the options level by level, and Optuna steers only after the block.

Retraining the finalists

The best score in a search is partly luck: each trial is one training run, and the highest of hundreds of noisy scores sits above the network's true level. So when the search ends, its top few networks are trained again from scratch with three new seeds each, with no early stopping, and the winner is the network with the best average validation score. The test set is still not used.

6.7What the search writes down

A search can run for days, and one that crashes near the end should not lose its results, so every result is written to disk the moment it arrives. Only one process writes, which keeps parallel trials from interleaving their lines.
