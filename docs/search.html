Chapter 6 · The Search

Hundreds of experiments,
run by machines, judged fairly

Depth, kernels, channels, pooling, τ, thresholds, dropout, norm, optimizer, learning rate, schedules… multiplied out, the design space has millions of corners. This chapter explains the machinery that explores it — Optuna proposes, Ray Tune orchestrates, ASHA executes the stragglers — and the quietly radical decision at its center: the score being optimized is the accuracy of the network after folding, quantization, and hardware neuron dynamics. Nothing else counts.

6.1The cast of characters

  • Optuna — the strategist. A Bayesian-ish optimizer (TPE): it looks at every finished trial's (config, score) pair and proposes the next config, spending more samples near what's been working, while still exploring.
  • Ray Tune — the factory manager. Launches each proposed config as its own process (one CPU + one GPU per trial), on this machine (--compute local) or across a cluster (--compute cluster), collects the metric reports each trial emits, checkpoints the search itself.
  • ASHA — the executioner. Watches every trial's per-epoch accuracy curve and kills trials that are clearly behind at scheduled checkpoints ("rungs"), freeing their GPU for fresh configs. The file quotes ~2.6× throughput.
  • The seeds — three known-good configs (SEED_CONFIGS) evaluated first, "so the search branches out from the winners instead of rediscovering them." With an honest caveat attached: their old scores came from the old float objective, so they're kept as geometry priors whose numbers "will not reproduce."

6.2Three tiers: every trial earns its GPU time

The heart of the search is trainable(config) — the function each Ray process runs. It's a funnel with three progressively more expensive gates:

  1. Tier 1 — feasibility. Cost: microseconds. The chapter-4 wiring check, before touching a GPU. Infeasible → report score 0 and exit immediately. (Earlier versions crashed on impossible configs — a collapsed feature map threw an exception mid-build; now the planner catches it as data, not disaster.)
  2. Tier 2 — float training. Cost: minutes-to-hours. Purpose: a pruning signal, NOT the score. The warmup + on-grid phases from chapter 5, reporting float_val_accuracy every epoch. This dense trajectory exists so ASHA has something continuous to judge trials by.
  3. Tier 3 — deployment. The only report that counts. Fold, quantize, export, evaluate: hw_val_accuracy. If deployment_report says undeployable (a folded threshold ≤ 0), the score is 0 — "regardless of how good its float accuracy looked."
🎭
The subtle trick: one name, two meanings — on purpose

Each trial's reports carry two metrics. float_val_accuracy: the per-epoch float curve, which ASHA prunes on. val_accuracy: holds the float number during training but the hardware number in the final report — and Optuna selects with scope="last", so it only ever learns the hardware number. A scheduler watching val_accuracy would compare float epochs against hardware finals — two different quantities — which is exactly why ASHA is pointed at the float curve and selection at the last report. The comments defend this wiring line-by-line against future "simplification."

🪤
The best bug story in the file: max_t = epochs + 1

ASHA stops any trial that has reported max_t times. Every tune.report() increments the counter — and the deployment result is one extra report after the last epoch. Set max_t = epochs and ASHA kills each trial at its final epoch, the deploy report never lands, hw_val_accuracy is NaN for every trial, "and selection quietly falls back to float accuracy — i.e. exactly the behaviour this whole rework exists to remove." The symptom is silent. The fix is + 1.

6.3ASHA, hands-on

The rules: every trial is guaranteed grace_period epochs (default 8). Then, at rungs placed at grace × rfk epochs (rf = reduction_factor, default 3), a trial survives only if it's in the top 1/rf of trials that reached that rung. Two design notes from the comments: grace must stay > 1 partly because cosine/onecycle schedules "do their work late — early judging favours flat-LR configs," and partly so instantly-rejected infeasible trials (one report at epoch 0) never form a rung and can't drag the cutoff down.

6.4Define-by-run: a search space with an if-statement in it

Most tools take a flat dictionary of ranges. But this space is conditional: a 4-layer network has a kernel size for layer 3; a 2-layer one doesn't. If the space were flat, Optuna's model would see a k_3 value on every trial — including trials where it had no effect — and learn nonsense correlations from it. Optuna's define-by-run API fixes this: the space is a function that runs per trial, calling trial.suggest_* only for parameters that exist on this trial's path, "so Optuna's surrogate never sees a dimension that had no effect on that trial's score."

6.5A search space with citations: what 65 trials taught it

The ranges aren't guesses — the space was narrowed by statistics from a previous 65-trial study, and every narrowing is annotated with its evidence in the comments. A tour of the receipts:

KnobNowThe evidence in the comments
channels{32, 64}128/256 were "the dominant INFEASIBILITY driver (chi-square p=6e-4, Cramér's V=0.59: 32ch 88% feasible, 128ch 14%) and never beat 32/64 on accuracy. Dropped."
kernel{5, 7}"every top-10 model used k5 or k7; k3 dropped."
depth2–4"winners are depth 2-3 (Kruskal-Wallis favoured shallow, q=0.08); depth 5 only ever reached 0.77."
hidden FC layers0–1"every top-10 model had 0 hidden FC (q=0.04), so 2-3 hidden layers are pure waste."
norm{bn, tdbn}"norm=none is GONE: it produced every dead (below-chance) network (p=0.0015; learned-vs-dead odds ratio 21.8)." Keeping bn vs tdbn makes them a clean A/B on the good backbone.
resize_to{32, 64}Native 128 "is omitted: 128·128·2 = 32,768 axons is over the 16,383 limit, so it could never pass feasibility."
lr5e-4 – 5e-3 (log)"positive correlation (Spearman q=0.04); winners are 1.6e-3..3.5e-3, so drop the under-converging low end."
τ (leak){2,3,4,6,8,16,32,63}Re-opened, not narrowed: the old float τ∈[1.5,2.5] finding (ρ=−0.60) was "a correlation with a coordinate the hardware cannot represent — it does not carry over."
weight decayfloors raised"the main lever on whether FOLDED weights fit inside [−1,1] … old floors (1e-8) were fitted against a float objective that could not see clipping."

Notice the two kinds of decision: knobs narrowed because the evidence transfers to the new objective (geometry), and knobs deliberately re-opened because their evidence was an artifact of measuring the wrong thing (τ, weight decay). Distinguishing those two is the difference between learning from data and overfitting to a broken metric.

6.6Crash-proof bookkeeping: the results directory

Ray's own final export only materializes after the whole search returns — so "a crash or Ctrl-C 30 hours into a search leaves you nothing." ResultsWriter fixes that by streaming every result to disk the moment it happens: append-a-line, flush, fsync — the files are complete between writes and watchable live with tail. Bigger multi-line files are written to a temp name and atomically renamed, so there is never a half-written best.json. And because Ray trials are separate processes, all writing happens in a single driver-side callback — no interleaved garbage.

One more piece: TargetAccuracyStopper. Ray's built-in stop condition only stops the trial that hit the target; stopping the whole study needs stop_all(). And it only triggers on a deploy-phase, deployable report ≥ target — "a float epoch that crosses the target says nothing about what runs on chip."

🏁
The chapter — and really the whole file — in one rule

Prune on the cheap signal, select on the true one, and make the true one the accuracy of the exact artifact that ships. Every engineering choice here (metric split, funnel tiers, deploy-only stopping, hardware-ranked leaderboard) is that one rule applied somewhere new.
