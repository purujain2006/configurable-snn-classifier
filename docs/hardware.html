Chapter 4 · Hardware & Quantization

The chip's house rules
(and how training obeys them)

A GPU runs whatever you write. HiAER-Spike runs only what it is: finite wiring, 16-bit integers, weights clamped to [−1, 1]. Two questions rule this chapter — feasibility (can it be wired at all?) and quantization (will the numbers survive?) — plus the training scheme that makes both answers "yes" by construction.

4.1Wiring budgets: fan-in, fan-out, axons

On a neuromorphic chip, a synapse isn't a number in a matrix — it's a physical routing entry. Routing tables are finite. That becomes hard limits, transcribed in the code as plain dictionaries:

Practice2.py§3
AXON_LIMITS = {
    "total_axons": 16_383,
    "fan_out": 4_096,   # axonal fan-out: how many neurons one input axon feeds
    "fan_in": 8_191,    # axonal fan-in: how many axons feed one neuron
}
NEURON_LIMITS = {
    "fan_out": 4_095,   # neuron-to-neuron fan-out
    "fan_in": 8_159,    # neuron-to-neuron fan-in
}

Vocabulary, with the picture to hold in your head:

  • Axon — an input line into the chip. The raw camera pixels enter on axons, so a 128×128×2 input needs 32,768 axons… and the budget is 16,383. Native resolution cannot even enter the chip — which is why every searched config resizes to 64 or 32 first.
  • Fan-in of a neuron — how many sources feed it. For a conv neuron this is its receptive window: k² · Cin. For a fully-connected neuron it's the entire previous layer's size.
  • Fan-out of a neuron — how many downstream neurons it feeds. For a conv feeding a stride-s conv with kernel k: each source pixel lands in about ⌈k/s⌉² · Cout windows.
INTERACTIVE Fan budget calculator — why 128 channels died in the search These are the exact formulas check_feasibility applies per layer. Bars show each quantity against its limit.

The empirical punchline, from the file's own comments after 65 real trials:

  • Channels were the #1 infeasibility driver: "32ch 88% feasible, 128ch 14%" — and big channel counts never won on accuracy anyway. The space was narrowed to {32, 64}.
  • Hardware pressure redesigns networks: small kernels shrink fan-in; small channel counts shrink both fans.
  • Flatten-into-FC is the most dangerous move: a 9,216-wide flatten exceeds the 8,159 fan-in limit all by itself.

How the full check walks the network

check_feasibility() (used live in chapter 3's builder) applies those formulas everywhere, with two corrections the comment calls out — both bugs in the earlier version:

  • Block 0 consumes axon budgets (it reads camera input); every later block uses the neuron budgets.
  • The last conv block's fan-out is the first FC layer's width — there is no next conv for the conv formula to describe.
  • The FC head is checked at all — previously it wasn't, and giant flattens sailed through unexamined.

Everything is arithmetic on the §2 plan — microseconds, no GPU — which is what makes it usable as a free gate in front of the hyperparameter search (chapter 6).

4.2The INT16 grid: what numbers survive on chip

Inside the chip there are no floats. The conversion library quantizes with fixed settings this file mirrors as constants — "every constant here is read off hs_api, not chosen":

w_delta = w_alpha / (2w_bits−1 − 1) = 1 / 32767 ≈ 0.0000305 The grid step. Every weight becomes one of the 65,535 multiples of w_delta in [−1, +1]; every threshold becomes the integer round(θ / w_delta).

Three consequences, each of which the float world never shows you:

  1. Weights are clamped to [−1, +1] — silently. With w_alpha fixed at 1 there is no rescaling: a weight of 1.3 simply becomes 1.0. No error, no warning — "nothing in the stack warns about it." The file names this the dominant source of float-to-chip accuracy loss.
  2. Thresholds must live in (0, 1]. θ quantizes to int(θ·32767): θ=1.0 lands exactly on the max integer; above it the field overflows; at or below 0 the neuron fires every step (chapter 2).
  3. The leak is an integer. τ deploys as round(τ) — chapter 2's plateau demo.

Inside ±1 the grid is so fine the loss is ~10⁻⁵ — rounding is nearly harmless. The damage is entirely the clamp. Which raises the question this chapter turns on: what pushes trained weights past ±1 in the first place? Answer: the next section.

4.3BatchNorm folding — the step that breaks networks

Three facts collide here:

  • BatchNorm (BN) sits after each conv, re-centering and re-scaling every channel's activations (running stats μ, σ²; learned scale γ and shift β per channel).
  • Networks need it: the search found norm="none" produced every single dead network in the study.
  • The chip doesn't have it. Before deployment, BN must disappear.

Luckily it can disappear exactly: conv + BN are two linear operations, and two linear operations compose into one. "Folding" bakes BN into the conv weights:

W′c = Wc · γc / √(σ²c + ε)      b′c = βc − μc · γc / √(σ²c + ε) Per output channel c. In floating point this is EXACT — the folded network computes bit-identical pre-neuron currents, hence identical spikes. (b′ is nonzero even though the convs are built bias-free.)

Two problems hide in that innocent formula, and they drive everything else in this chapter:

PROBLEM 1 The scale factor inflates weights
  • γ/√(σ²+ε) is often > 1 — and folding multiplies every weight in the channel by it.
  • Healthy weight 0.6 × channel scale 2.1 → 1.26 → the INT16 clamp silently amputates it to 1.0.
  • Folding is precisely the step that pushes weights out of range. Train float → fold → quantize = accuracy off a cliff, invisible in float metrics.
PROBLEM 2 Where does b′ go?
  • The fold manufactures a per-channel bias b′ — but the chip's neuron has no bias input.
  • bias_mode="conv": keep b′ on the conv. Exact, but needs on-chip conv-bias support.
  • bias_mode="threshold" (the deployment route): hide it in the neuron. Adding b′ every step ≡ lowering the threshold to θ′ = θ − b′, per channel — and per-neuron thresholds are native on this chip. Free.

4.4Fake quantization & the straight-through estimator

How do you train weights that will be clamped and rounded? Rounding has zero gradient — the same disease as the spike in chapter 2, and the same cure. Every conv/linear weight gets wrapped in fake quantization:

Practice2.py · fake_quantize_weight§4b
def _ste(quantized, original):
    """Straight-through estimator: forward uses `quantized`, backward passes
    the gradient to `original` unchanged."""
    return original + (quantized - original).detach()

def fake_quantize_weight(w):
    b = W_BITS - 1                                  # 15
    levels = 2 ** b - 1                             # 32767
    wc = torch.clamp(w / W_ALPHA, min=-1.0, max=1.0)
    q = torch.round(wc.abs() * levels) / levels * torch.sign(wc) * W_ALPHA
    return _ste(q, w)
  • Forward: the network computes with the clamped, rounded weight — bit-exactly what the chip will store.
  • Backward: the gradient flows to the underlying float as if nothing happened. The _ste one-liner is the whole trick: original + (quantized − original).detach() equals quantized in value, but its derivative w.r.t. original is exactly 1.
  • "The clamp is the part that matters" (the code's words): clamping inside the forward pass makes an out-of-range folded weight hurt the loss immediately — the optimizer routes around it — instead of surprising you after conversion.
  • Same pattern everywhere: thresholds (fake_quantize_threshold) and the learnable integer τ use the identical STE trick.
  • Damage meter: weight_clip_fraction() = share of weights outside ±1. Call it on the folded net — "pre-fold numbers are meaningless."

4.5Quantization-aware training: three strategies, one winner

TrainSpec.qat_mode selects how a run reaches the deployable INT16 network. From weakest to strongest:

ModeRecipeCharacter
"ptq"Train fully in float → fold BN → quantize once → measure.Post-training quantization. The honest baseline: measures how much damage fold+clamp does to a network that never saw them coming.
"tail"Train fully in float → fold → quantize → a few fine-tune epochs on the grid (qat_epochs, at qat_lr_scale·lr).The older approach: quantization as a repair job bolted on the end.
"inline"Short float warmup (qat_warmup_frac ≈ 25% of epochs, so BN's running statistics become trustworthy) → fold inline → train the entire rest of the run on the folded, quantized grid.The default. "The network never gets to build the precise-weight balances that ordinary float training leans on and that post-hoc quantization then shatters."

At the fold point, every (Conv, BN) pair is physically replaced by one ConvBNFoldQuant module. Its forward pass re-folds from BN's running statistics every step (batch statistics would make the deployed weight flicker per-minibatch), fake-quantizes W′, and hands b′ to the downstream neuron as a per-channel threshold shift — the _fold_bias hook you saw in chapter 2's forward pass. BN's γ, β and running stats keep updating from a cheap statistics-only pass, so the fold tracks the data as training proceeds.

Freezing the deployable artifact

After training, export_deployed() freezes the network: each ConvBNFoldQuant becomes a plain bias-free conv with the final quantized weights; b′ is baked into per-channel thresholds. Exactly what the converter consumes — nothing left to fix up. Two report functions then gate and package it:

  • deployment_report() — legality audit. BLOCKING (score 0, config rejected): any folded threshold ≤ 0. WARNING (allowed, surfaced): more than 2% of weights clipped. The warning is deliberately not a rejection — QAT trains against clipping, and the hardware-accuracy metric already prices in surviving damage.
  • hardware_export() — emits per-layer integer thresholds and integer leaks as JSON. The comment records why this exists: the conversion script used to hardcode threshold = 32767 and leak_lif = 63 globally — "those two lines are why per-layer neurons were impossible."

4.6Trust, but verify the fold

A wrong fold looks like a mediocre model, not a crash. So verify_fold() compares the BN network against its folded twin at three levels, ordered so failures localize the bug:

  1. Prediction agreement. Fraction of samples where both networks pick the same class. For an exact (conv-bias) fold this must be 1.0 — anything less is a bug, not noise.
  2. Max |logit difference|. ~10⁻⁵ for a correct fold in fp32. A large value with high agreement means "subtly wrong" — the most dangerous quadrant.
  3. Both accuracies. Only now the headline number — because "test accuracy alone is too coarse to catch a subtly wrong fold."
  • Related guard: fold_bn refuses to run on a network in training mode — BN would supply batch statistics instead of running ones, "the single most common cause of a 'folding lost accuracy' report."
This chapter in one sentence

Feasibility says the wiring fits; folding + fake quantization say the numbers fit; inline QAT makes both true during training rather than checking them after; and the reports turn "will it work on the chip?" from a hope into a boolean the search can optimize.
