Fitting the chip

A configuration must fit the connection limits and use representable weights and neuron parameters. The examples below show the checks, integer mapping, and changes needed when batch normalization is removed.

4.1Connection limits as arithmetic

An input axon carries an external input into the device. Fan-in counts connections arriving at one neuron; fan-out counts connections leaving one source. These are routing limits, separate from the number of learned weights. The package currently uses 16,000 input axons, the tested ceiling recorded for the L6m bitstream, rather than the field's representable maximum of 16,383.

Implementation details

The hardware stores connections in tables with fixed capacity. A configuration that exceeds a connection limit must be rejected before deployment.

The layer plan from section 3.2 provides the dimensions needed to check connection limits before training. This avoids spending training time on infeasible configurations.

check_feasibility() walks the plan and returns a boolean with a list of violations. The search calls it before allocating any hardware, and reports a score of zero for configurations that fail.

Source excerpt

    "fan_in": 8_159,    # neuron-to-neuron fan-in
}

The quantities compared against those limits are:

  • Fan-in of a convolution neuron is k² · Cin, the size of the window it reads.
  • Fan-out of a convolution neuron is ⌈k/s⌉² · Cout, the number of windows in the next layer that contain it.
  • Fan-in of a linear neuron is the full width of the previous layer.
  • Input axons are height × width × channels of the input.

The first block draws on the axon budget because it reads the input. Later blocks use the neuron budgets. The last convolution block is a special case: its fan-out is the width of the first linear layer, since no further convolution follows it.

The comments in the search space record what these limits did to the design after 65 trials. Channel count was the strongest predictor of infeasibility: 88% of 32-channel configurations passed, against 14% of 128-channel ones, and the wider networks never scored better. The sampled set was reduced to 32 and 64 channels. A wide flatten is the other common failure, since 9,216 features exceed the 8,159 fan-in limit on their own.

4.2The INT16 grid

INT16 means a signed 16-bit integer representation. Quantization maps real-valued parameters to the supported discrete values. Here w means a weight, w_alpha sets the real value represented by the largest positive integer, and w_delta is the spacing between adjacent representable weights.

The chip holds 16-bit signed integers, so the values that physically exist on the device run from −32767 to +32767. A trained weight of 0.7 has to be scaled to one of them before it can be deployed.

w_alpha

w_alpha sets what real value the largest integer, 32767, stands for. That single number fixes the whole mapping.

store:   n = round( w / w_alpha × 32767 )      read:   w = n × w_alpha / 32767 With w_alpha = 1 the integer 32767 represents the value 1.0. With w_alpha = 5 it represents 5.0.

A larger range sacrifices a bit of resolution:

w_alpha = 1
32767 is 1.0, so the range is [−1, 1] and a weight of 1.3 must be truncated to 1.0.
w_alpha = 5
32767 is 5.0, so the range is [−5, 5] and a weight of 1.3 stores as round(1.3/5 × 32767) = 8519 while being read back as 1.29997.

Where it appears

The value originates in the converter. snnsearch/hardware.py mirrors it rather than choosing one of its own, so training and conversion agree on what each stored integer means.

Source excerpt
snnsearch/hardware.pythe INT16 grid
W_ALPHA   = 1.0                        # read off the converter, not chosen here
INT16_MAX = 2 ** (W_BITS - 1) - 1      # 32767
W_DELTA   = W_ALPHA / INT16_MAX        # 1/32767, the spacing between grid points

def fake_quantize_weight(w):
    wc = torch.clamp(w / W_ALPHA, min=-1.0, max=1.0)     # truncation
    ...

def quantized_threshold_int(th):
    return clamp(round(th / W_DELTA), 1, INT16_MAX)      # thresholds share the scale

The converter is constructed as Quantize_Network(w_alpha=1, dynamic_alpha=False, w_bits=16). Most quantization schemes set the scale to fit the data, usually to the largest weight present, which is what the word dynamic refers to. Here it is switched off and the scale is pinned, so weights outside the range are truncated rather than mapped proportionally.

Thresholds are mapped to the same scale, which is why θ has to stay within (0, 1]. A neuron compares its membrane potential against θ, and that potential is a running sum of weights. Giving weights a scale of their own would put the two sides of that comparison in different units, so every threshold would need rescaling by the same factor to stay meaningful.

Within the representable range, rounding error is on the order of 10−5. Clipping values outside that range can cause larger changes, especially after batch-normalization folding.

4.3Removing batch normalization

Batch normalization rescales each channel using running statistics and learned parameters. The chip has no normalization layer, so conversion folds this transformation into neighboring parameters. Earlier search comments claimed normalization was essential, but the local 82-trial analysis did not support that general claim.

Removal is exact. A convolution followed by batch normalization is one linear map followed by another, and the pair composes into a single convolution:

W′c = Wc · γc / √(σ²c + ε)      b′c = βc − μc · γc / √(σ²c + ε) Per output channel c. In floating point the folded network delivers the same input to every neuron, so it produces the same spikes.

Folding changes the scale of the weights and introduces a bias. Both changes need to be handled during conversion.

Folding parameters for the hardware

The scale factor γ/√(σ²+ε) is frequently greater than 1, and folding multiplies every weight in the channel by it. A trained weight of 0.6 in a channel with a scale of 2.1 becomes 1.26, which section 4.2 truncates to 1.0.

Folding is the step that moves weights outside the representable range, so a network trained in floating point and folded afterwards can lose accuracy that no training metric predicted. Weight decay becomes relevant to deployment, since it controls how far the folded distribution spreads.

weight_clip_fraction() measures the proportion of folded weights outside the range, and deployment_report() warns above 2%. The search samples weight decay from ranges whose lower bounds were raised once this became measurable.

Weight decay can limit the magnitude of folded weights as well as regularize training. Whether clipping remains a problem must be checked on the folded values before clamping.

Folding parameters for the hardware

The fold produces a per-channel bias b′, which is non-zero even when the convolution was built without one. Convolutions on the chip have no bias field to receive it.

A per-channel threshold can store the bias adjustment produced by folding. This keeps the representation compatible with the chip, but is not generally equivalent to injecting that bias on every timestep. The comparison below explains the temporal difference.

fold_bn(net, bias_mode="threshold") writes θ′ = θ − b′ into the following neuron and leaves the convolution bias-free. bias_mode="conv" keeps b′ on the convolution instead, which is exact and useful for verification in software.

Threshold-mode folding needs θ′ = θ − b′ > 0, so it needs θ > b′. Since fake_quantize_threshold caps θ at w_alpha = 1, the implied b′ of at least 1.588 is above every θ the encoding permits. No choice of threshold rescues that fold.

Folding parameters for the hardware

In the floating-point model, the folded bias is β + (conv_b − μ) · scale. Without an explicit constraint, learned β can make this bias incompatible with the threshold encoding. The deployment check then rejects the result.

The legality band has to be enforced while the network trains, so the network adapts to it rather than meeting it once at the end. The band is two-sided, because the other end fails silently as well: quantized_threshold_int saturates at INT16_MAX, so a θ′ above w_alpha deploys as w_alpha with no error raised.

constrain_fold_bias clamps b′ into [θ − w_alpha, θ(1 − margin)] inside ConvBNFoldQuant._folded_weight_bias, using the same clamping arrangement as the weight quantizer. The forward pass uses the clamped value, so the loss responds to the constraint, and the gradient still reaches β so the optimizer can move toward a legal value on its own. The margin is TrainSpec.fold_bias_margin, default 0.05, and setting it to 0 restores the previous behavior.

Source excerpt
snnsearch/quantgrid.pythe constraint
def fold_bias_band(v_th: float, margin: float = 0.05):
    lo = float(v_th) - W_ALPHA                 # keeps theta' <= w_alpha
    hi = float(v_th) * (1.0 - float(margin))   # keeps theta' >= margin*theta
    return lo, hi

def constrain_fold_bias(b, v_th, margin: float = 0.05):
    lo, hi = fold_bias_band(v_th, margin)
    return _ste(torch.clamp(b, min=lo, max=hi), b)

With θ = 1 and the default margin, the band is [0, 0.95]. The b′ of 1.588 that produced the rejection above is clamped to 0.95, giving θ′ = 0.05, which stores as the integer 1,638. Every value of b′ now yields a θ′ inside (0, w_alpha] by construction.

A bias and a lower threshold are not the same thing

A legal stored threshold does not by itself establish equivalent neuron dynamics. The following comparison tests the bias and threshold forms.

A bias adds current on every timestep. A threshold shift changes the firing boundary. These operations generally produce different state trajectories, including when repeated input accumulates without leak.

Folding parameters for the hardware

During a period without spikes or resets, a constant input bias contributes a membrane offset that approaches b′·τ for the update rule used here. A fixed threshold shift does not reproduce that changing offset.

Because the bias contribution varies over time and resets after spikes, a fixed threshold adjustment cannot generally reproduce it. Training should therefore use the same threshold form that export writes.

TrainSpec.fold_bias_qat_form defaults to "threshold", so HardwareLIFNode compares against θ − b′ during quantization-aware training, which is what export_deployed writes. Setting it to "input" restores the previous behavior for comparison. fold_bias_report now also reports |b′|·τ/θ, since the older |b′|/θ ratio carries no leak term.

The alternative, if the converter can be changed

4.4Training on the grid

Training through quantization

Quantization and folding can change the network’s outputs. Applying them during training allows the optimizer to respond to these changes. Since rounding has zero derivative almost everywhere, the backward pass uses an approximate gradient.

During quantization-aware training, the forward pass uses quantized weights. The optimizer updates separate floating-point parameters through an approximate gradient. It can therefore respond to the effect of quantization while retaining small parameter updates.

fake_quantize_weight clamps and rounds forward, and _ste sends the gradient to the float parameter unchanged. The same helper handles thresholds and the learned integer leak from section 2.3.

Source excerpt
snnsearch/quantgrid.pyfake_quantize_weight
def _ste(quantized, original):
    """Straight-through estimator: forward uses `quantized`, backward passes
    the gradient to `original` unchanged."""
    return original + (quantized - original).detach()

def fake_quantize_weight(w):
    b = W_BITS - 1                                  # 15
    levels = 2 ** b - 1                             # 32767
    wc = torch.clamp(w / W_ALPHA, min=-1.0, max=1.0)
    q = torch.round(wc.abs() * levels) / levels * torch.sign(wc) * W_ALPHA
    return _ste(q, w)

The expression original + (quantized − original).detach() equals quantized numerically, while its derivative with respect to original is exactly 1.

Raw and quantized weights

Quantization-aware training retains a floating-point parameter for optimization and computes a quantized value for the forward pass.

stored value
An ordinary parameter with no limits on it, and the one the optimizer updates. It lives at module.parametrizations.weight.original.
used value
The stored value after clamping and rounding. The network multiplies with this one, and reading module.weight returns it.

Clamping affects the value used in the forward pass. If the underlying floating-point parameter is 1.3, it remains 1.3 while the network computes with 1.0. Export saves the quantized value.

Training through quantization

Keeping the underlying floating-point parameter allows small optimizer updates to accumulate even when rounding leaves the forward value unchanged.

As the floating-point parameter moves from 1.3 toward 0.9, the forward value remains clamped at 1.0 until the parameter reenters the representable range.

_WeightFakeQuant is registered through torch.nn.utils.parametrize, which keeps the raw parameter and computes the clamped version on each read. bake_weight_fake_quant collapses the two into one at export, so the saved network holds the values the chip receives.

The boundary behavior depends on weight scale, weight decay, and the approximate gradient.

  • In the recorded runs, unfolded convolution weights typically remained below the clipping boundary. Folding can increase their magnitude.
  • Weight decay pulls every weight toward zero in proportion to its size, so the further out a stored value travels the harder it is pulled back.
  • Once the forward value is clamped, further increases in the raw parameter do not change that forward value.

The third point holds for the network's output but not for the gradient. A true derivative would be zero past the boundary, and the straight-through estimator returns 1 there instead, so the optimizer can keep pushing a stored value outward to no effect. Weight decay is what balances that. This behavior is characteristic of straight-through quantization generally rather than specific to this implementation.

A metric this invalidates

weight_clip_fraction counts weights whose magnitude exceeds 1, and it reads m.weight, which is the used value. The used value is clamped to 1 before it can be read, so the count is structurally zero and the function reports 0.0% whatever the network is doing. It measures whether the clamp worked rather than whether the clamp had anything to do.

max_abs_weight also reads the clamped tensor. A value of exactly 1.0 can indicate boundary contact, while the recorded maximum of 0.665 indicates no clipping in that inspected tensor. To measure the fraction requiring clipping, inspect module.parametrizations.weight.original before clamping.

Follow a weight through training and export

With w_alpha = 1, the converter represents weights between −1 and 1 using integer steps of 1 / 32767. A raw weight of 0.7 becomes integer 22,937 and is read back as approximately 0.700003.

A raw weight of 1.3 lies outside the range. The forward pass uses 1.0, but the optimizer retains the raw 1.3 parameter. Updates can move that parameter through 1.2, 1.1, and 1.0 before the forward value starts changing again. Smaller updates within the range can also accumulate across quantization steps.

Rounding has a zero derivative almost everywhere. The straight-through estimator supplies an approximate derivative of 1 so the optimizer can continue updating the raw parameter. This is an approximation used for training, not the mathematical derivative of rounding.

Folding batch normalization can move a weight across the boundary. A weight of 0.6 multiplied by a channel scale of 2.1 becomes 1.26, which clips to 1.0. Measure clipping on the folded value before the clamp. Inspecting the already clamped value would report no out-of-range weights.

4.5Folding during training rather than after

Three schedules are available through TrainSpec.qat_mode.

ModeSchedulePurpose
ptqTrain in floating point, then fold and quantize once.A baseline that measures how much the conversion costs a network that never saw it.
tailTrain in floating point, fold, quantize, then fine-tune for a few epochs.Treats quantization as a repair applied at the end.
inlineWarm up in floating point for about a quarter of the budget, fold in place, and train the remainder on the folded and quantized network.The default. Most of training happens on the network that will deploy.

The warm-up exists because folding reads batch normalization's running statistics, which need a few epochs of data before they are meaningful. After the fold, each convolution and batch normalization pair is replaced by a single ConvBNFoldQuant module. Its forward pass recomputes the fold from the current running statistics, quantizes the result, and passes the per-channel bias to the neuron through the _fold_bias attribute seen in section 2.6. The statistics themselves keep updating from a separate pass over the raw convolution output, so the fold tracks the data as training continues.

Clipping before and after training

The clamp of section 4.2 is the same operation in all three schedules, but its effect on the result depends on whether training happened before or after it.

ptq quantize after training
  • The optimizer settles on a weight of 1.26, because that value minimized the loss it was shown.
  • Conversion truncates it to 1.0.
  • The deployed weight differs by 0.26 from the value used during floating-point validation. Its effect on accuracy must be evaluated after conversion.
inline quantize during training
  • The clamp is already inside the forward pass, so an attempt to use 1.26 computes with 1.0 and the loss reflects 1.0.
  • The forward value remains clamped at 1.0. The approximate gradient may still move the underlying parameter outside the range, so this does not guarantee an in-range floating-point weight.
  • Export retains the quantized weights used during training. Other aspects of conversion, including neuron state updates and threshold folding, still require verification.

With post-training quantization, the converted network may differ from the one selected during training. With inline quantization, the optimizer already sees the constrained forward values. Widening the range changes the available solutions, but does not guarantee an accuracy improvement.

Freezing the result

export_deployed() converts each ConvBNFoldQuant into a plain bias-free convolution holding the final quantized weights and writes the folded bias into per-channel thresholds. What remains is the network the converter consumes. Two functions then inspect it:

  • deployment_report() checks legality. A folded threshold at or below zero blocks deployment and scores the configuration zero. More than 2% of weights outside the range produces a warning rather than a rejection, since quantization-aware training has already been given the chance to work around the clamp.
  • hardware_export() writes the integer threshold and integer leak for each spiking layer as JSON. The conversion script previously carried a single hard-coded threshold and leak, which prevented per-layer neuron parameters from being used at all.

4.6Verifying the fold

An incorrect fold lowers accuracy without raising an error, so accuracy alone is a weak test. verify_fold() compares the network before and after folding at three levels, in an order that isolates the cause of a failure.

  1. Prediction agreement The fraction of samples where both networks choose the same class. With the bias kept on the convolution this should be exactly 1.0.
  2. Largest difference in class scores The 11 numbers the network produces per clip, compared one by one. Around 10−5 in 32-bit floating point for a correct fold. A large value alongside high agreement indicates an error that accuracy would not reveal.
  3. Accuracy of both networks Reported last, once the first two have established that the transformation itself is sound.

fold_bn also refuses to run on a network in training mode. Batch normalization would then supply batch statistics rather than running statistics, which is the most common cause of a fold that appears to lose accuracy.
