What the trials revealed

Four search runs are on record, holding 82 trials. The comments in Practice2.py that narrowed the search space cite statistics computed once, by hand, and never checked back in. This page recomputes every one of them from the raw trial files, reports which survive, and links each surviving result to the code it changed.

7.1The record

Each run writes a leaderboard, a rejection log, and one JSON record per trial. Nothing here is reconstructed from memory. The counts below come from those files.

Searches 1 and 2 predate the hardware objective. They score trials on floating-point validation accuracy, so their numbers describe a network before conversion. Searches 3 and 4 report hw_val_accuracy, which is the accuracy of the converted network, and are the only runs whose scores mean what the project needs them to mean.

  • 82 trials in total, of which 50 passed the connection check and 43 produced a score.
  • 33 of 43 scored trials were stopped early by ASHA. The median trial ran 8 epochs.
  • 2 trials in the entire record reached the deployment stage and reported a converted accuracy.

The seven feasible trials without a score were pruned before their first validation report landed. They count toward feasibility and cannot enter an accuracy comparison.

7.2Recomputing the recorded statistics

Observation

Several ranges in the search space were narrowed on the strength of statistics written into comments. Those numbers decide which configurations the search is allowed to try, so a wrong one silently removes good designs from consideration for the rest of the project.

Consequence

A claim that constrains future work has to be reproducible from the data that produced it. Each one was recomputed from the raw trial files, using permutation tests rather than asymptotic approximations, since 43 scored trials is too few for the usual large-sample arguments.

In code

tools/trial_analysis.py reads every leaderboard and rejection log, implements chi-square, Cramér's V, Kruskal-Wallis, Spearman and Mann-Whitney directly, and prints a verdict per claim. Its full output is kept alongside the site.

Claim in the fileRecordedRecomputedVerdict

Shallow networks score better q=0.08 H=11.41, p=0.005 holds

The one that does not reproduce

The normalization claim is the only recorded statistic the available data contradicts. Five trials in the record ran without normalization, and their accuracies overlap the normalized ones heavily:

tools/trial_analysis.py · claim 4
      norm    n   median     best  dead (<0.15)
        bn   31   0.6705   0.8352             1
      none    5   0.3182   0.7159             1
      tdbn    7   0.6307   0.6818             2

  permutation p=0.1956   P(normalized > unnormalized)=0.68
  [DOES NOT HOLD] the recorded p=0.0015 and odds ratio of 21.8 are not
  reproducible from these four runs

An unnormalized network reached 0.7159, which is close to the best result in its own run. The original figure came from an earlier study whose records are not in this repository, so this is a claim without recoverable evidence rather than a claim shown to be false. The practical consequence is the same: the comment in Practice2.py cites a number the project can no longer defend.

A nuance the comment misses

The file treats τ's correlation with accuracy as an artifact of sampling a continuous value that the chip rounds away. The first half is right and the second half is not.

tools/trial_analysis.py · claim 6
  sampled tau range: 1.520 to 3.980
  distinct sampled values : 41
  distinct DEPLOYED values: 3   ->  [2, 3, 4]

  continuous tau vs accuracy: rho=-0.491  p=0.0008
  deployed  tau vs accuracy: rho=-0.392  p=0.0100

Forty-one sampled values collapse onto three, so the resolution the search was exploring is indeed imaginary. The correlation survives the collapse: τ=2, 3 and 4 are genuinely different networks and lower values score better. Reopening the range was the right call, but the reason is that the search was measuring at the wrong resolution rather than measuring nothing.

7.3Where configurations died

Sixteen configurations were rejected before any GPU time, by the arithmetic check of section 4.1. Their recorded violations show which limit actually binds:

CountViolationWhat it means
7classifier / fc0 fan-inThe flattened feature vector is wider than 8,159, so the first linear layer cannot be wired. Values reached 230,400.
4spatial sizeThe feature map shrank below the kernel, so the layer cannot be built at all.
3conv fan-ink²·Cin above 8,159, from a wide input channel count.
2conv fan-outAbove 4,095 destinations from one neuron.

The flatten width dominates, and it is the one quantity a designer does not set directly. It follows from the last convolution's output volume, which is why the fan budget calculator on page 4 derives it rather than offering it as a control.

Channel count is what drove those failures. Across all four runs, feasibility falls off a cliff:

tools/trial_analysis.py · claim 1
   channels    n  feasible    rate
         32   32        30    94%
         64    9         7    78%
        128    7         0     0%
        256    7         0     0%

  chi2=39.42  dof=3  Cramer's V=0.85  permutation p<1e-4

Not one configuration above 64 channels was buildable. That is what removed 128 and 256 from the sampled set.

7.4The deployment stage

Observation

Two trials in 82 produced a converted accuracy. Everything else was pruned by early stopping, rejected by the connection check, or ran under the older objective that never converted anything.

Consequence

Every statement about how the network behaves after conversion rests on two data points. That is enough to have found two concrete failures and one working export, and nowhere near enough to characterize the conversion in general.

In code

The deploy-phase report carries hw_val_accuracy, quant_gap, weight_clip_frac, min_threshold and deployable. A configuration deployment_report marks undeployable scores zero whatever its accuracy was.

TrialFloatConvertedGapClippedDeployable
734747f00.69890.7443−0.04550.0%yes

Conversion did not cost accuracy

Both gaps are negative, meaning the converted network scored higher than the floating-point one. That is the intended behavior of the inline schedule rather than a surprise. The float figure is the best the warm-up phase reached before folding, and the remaining epochs train on the folded and quantized network, so the on-grid network keeps improving after the number it is being compared against stops moving.

Neither trial clipped a single weight. Combined with the largest folded weight sitting at 0.665 in the probe export, this is the evidence that the weight-range problem of section 4.3 is not currently binding.

What blocked the second trial

results (4) · trial 973e6c46
val_accuracy       0.0            ← scored zero for being undeployable
hw_val_accuracy    0.5284         ← what it would have achieved
weight_clip_frac   0.0
deploy_reasons     folded threshold -0.5877 <= 0 -- neuron fires unconditionally

The scoring rule is doing its job here. A network that fires unconditionally is worthless on chip regardless of what it scored in simulation, so the search records zero and moves on. This trial and the probe run are the two failures that motivated the folded-bias constraint in section 4.3.

Two trials produced no report at all

Of the four trials that ran to completion under the hardware objective, two produced no deployment report. Both stopped at exactly their configured epoch count:

TrialEpoch budgetEpochs runDeployment report
734747f01516arrived

The trial that reported ran one iteration past its budget. The two that did not stopped exactly on it. That pattern is the signature of the max_t problem described in section 6.3, where a trial is stopped on its final epoch and the deployment report never lands. The logs do not record a cause, so this is a matching symptom rather than a confirmed diagnosis, and it is worth re-checking on the next run.

The best configuration found so far is small and plain:

results (2) · trial c766d47ebest float accuracy, 0.8352
--input   resize_to=64 T=16
--encoder depth=2 channels=32 kernel_size=7 stride=2 norm=bn
--head    final_reduction=flatten fc_widths= dropout_rate=0.29
--neuron  tau=2
--train   optimizer=adam lr=0.0029 weight_decay=2e-7 scheduler=none

Two convolution layers, 32 channels, no hidden fully connected layer, no learning rate schedule. Every direction the search was given room to explore, it declined to use.

The gap to the target is large, and these runs do not show whether it can be closed, because nothing has been trained long enough to find out. The median trial ran eight epochs against a budget of forty, and the two that converted ran thirteen and sixteen. Not one configuration in the record has been given a full training run and then converted.

7.6What each result changed

Every narrowing carries its evidence in a comment next to the line it constrains, so the reason a range exists is readable from the file rather than from a separate document.

Practice2.py · DefineByRunSpace§10
#   channels: 128/256 were the dominant INFEASIBILITY driver (chi-square p=6e-4,
#     Cramer's V=0.59: 32ch 88% feasible, 128ch 14%) and never beat 32

# fc_layers 0-1 only: every top-10 model had 0 hidden FC (Kruskal-Wallis
# q=0.04), so 2-3 hidden layers are pure waste. Keep 1 as a branch.

# lr: positive correlation (Spearman q=0.04); winners are 1.6e-3..3.5e-3,
# so drop the under-converging low end (was 1e-4).
trial.suggest_float("lr", 5e-4, 5e-3, log=True)

What the record does not support

  • The normalization statistic cited in the file cannot be reproduced from these four runs. The comment should either cite the study it came from or be re-derived.
  • No configuration has completed a full training budget and then been converted, so the converted accuracy ceiling is unknown rather than measured at 74.4%.
  • Both deploy-phase failures come from short runs whose batch normalization statistics were still immature, which inflates the folded bias. The size of that effect on a converged run has not been measured.
  • split_by is fixed at "number" in every run. The alternative has never been tried.

The full analysis output, including every test statistic and the per-run breakdown, is in docs/data/trial_analysis.txt. It regenerates with python tools/trial_analysis.py <results root> and needs only numpy and pandas.
