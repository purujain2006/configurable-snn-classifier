Chapter 5 · Data & Training

From event stream
to learned gestures

This chapter follows a gesture clip through the whole training machinery: how millions of camera events become T tidy binary frames, how the network's spikes become a class prediction ("rate coding"), why every training batch runs extra empty timesteps at the end, and how the training loop is scheduled — including the moment mid-run when the network is swapped onto the chip's integer grid.

5.1The dataset: 1,342 clips of people waving

DVS128 Gesture contains recordings of 29 subjects performing the 11 gestures under three lighting conditions, captured by a 128×128 event camera. Each recording is a long list of events: (x, y, polarity, timestamp) — where, which direction the brightness changed (ON/OFF → the 2 channels), and when, at microsecond resolution. Loading goes through the SpikingJelly library's DVS128Gesture class, which the code asks for frame mode: chop each clip's events into T equal-count slices (split_by="number" — each slice holds the same number of events, so fast motion gets thin time slices and slow motion gets thick ones), then rasterize each slice by counting events per pixel. Result per clip: a tensor of shape (T, 2, 128, 128).

Three unglamorous decisions in build_dataloaders that careful readers should notice:

  • The validation split is seeded. torch.manual_seed(1) before the random 15% split — every run, every search trial, judges itself against the same validation set. Comparisons stay apples-to-apples.
  • drop_last only on the training loader. Dropping the ragged final batch is fine for training but on val/test it would silently discard up to N−1 samples "and bias every accuracy number reported."
  • num_workers=0, deliberately. Each search trial is already its own process; DataLoader workers would spawn processes inside processes — "nested multiprocessing like that is broken on Windows and would oversubscribe CPUs across concurrent trials."

Related engineering: warmup_dataset_cache() pre-builds SpikingJelly's frame cache for every T value before parallel trials launch (two trials racing to build the same cache folder can corrupt it), detects half-built caches by checking every class folder has samples, and wraps the noisy extraction in _quiet_with_heartbeat — which swallows hundreds of progress lines and prints one calm heartbeat every 20 s instead, dumping the full captured log only on failure. And validate_data_dir() turns the library's cryptic deep-stack FileNotFoundError into a message that tells you exactly which folder layout it expected.

5.2Resize + binarize: deliberately lossy, in a chosen direction

128×128×2 = 32,768 input axons; the chip allows 16,383. So frames are shrunk (to 64×64 or 32×32) and — because spiking input should be spikes, not gray values — snapped to {0, 1}. The transform is two lines with a subtle personality:

Practice2.py · DVSResizeAndBinarize§6
out[t] = F.interpolate(frames[t]..., size=self.size, mode="bilinear", ...)
return (out > 0).float()   # ANY nonzero contribution becomes a full spike

The docstring is explicit that this is not average-downsampling: bilinear interpolation of a sparse binary frame produces small fractional values, and > 0 promotes any nonzero contribution back to a full spike. "Effectively OR-pooling — no events are lost, but event density per pixel rises at low resolutions." A deliberate trade: preserve every scrap of sparse signal, accept busier pixels.

With the OR rule, a lone event always survives downsampling (density rises); with averaging it fades to a small gray value that a spiking input can't represent. Same story at 32×32, just stronger.

5.3Reading the answer: rate coding

After the last layer, there are 11 output neurons — one per gesture — each emitting spikes over time. The network's "answer" is defined as each output neuron's firing rate: total spikes accumulated across the run, divided by T. Highest rate wins (and during training, those 11 rates go into a standard cross-entropy loss exactly as if they were ordinary scores). This is rate coding — the simplest way to turn spike trains back into numbers.

But there's a wrinkle you already know from chapter 2: with the chip's fire-on-previous-step neuron, each layer delays everything by one timestep. The evidence from the final input frames is still in flight, somewhere mid-network, when the input ends.

5.4The pipeline flush: why the network runs on empty

The fix is forward_over_time(), and it mirrors the hardware conversion script's measurement exactly: feed the T input frames, then keep stepping the network for flush_steps extra timesteps with all-zero input — one per spiking layer — while continuing to accumulate output spikes. Then divide by T (not T + flush, so rates stay comparable across depths).

Turn the flush OFF and add layers: a 6-layer network quietly throws away the last 6 frames — 6/8 of the clip! This bug class is vicious precisely because nothing errors; accuracy is just mysteriously lower on hardware. Modeling the flush during training (every batch, every epoch) makes train-time and chip-time agree.

5.5The training loop, from the inside

One training step, spelled out for readers who haven't seen a PyTorch loop:

  1. Forward. A batch of clips (N, T, 2, H, W) goes through forward_over_time — the full T + flush simulation — yielding 11 firing rates per clip. The membrane states are then reset (functional.reset_net): clips must not leak into each other.
  2. Loss. Cross-entropy between rates and the true gesture, optionally softened by label_smoothing (the true class becomes e.g. 0.85 instead of 1.0 — a mild overconfidence penalty that the winning configs used at ~0.15).
  3. Backward. Backpropagation through time and through spikes: gradients flow back across all T timesteps, crossing every spike via the ATan surrogate (chapter 2) and every quantizer via STE (chapter 4).
  4. Step. Optional gradient clipping, optimizer update, optional per-batch scheduler tick.

After each epoch, evaluate() measures validation accuracy, and the best-scoring weights are kept (deepcopy of the state dict) — the final model is the best epoch, not the last one.

Optimizers & schedules

build_optimizer offers Adam, AdamW, and SGD — with a comment worth repeating because it bites people: in classic Adam, weight_decay is L2 added to the gradient and gets tangled with the adaptive step size; AdamW applies decay decoupled from it. Since chapter 4 showed weight decay doubles as a deployment lever (it keeps folded weights inside [−1,1]), the search gives the two optimizers different decay ranges. build_scheduler shapes the learning rate over epochs:

Why the search's early-stopper must respect schedules: cosine and onecycle do their best work late. Judge a trial at epoch 3 and you systematically favor constant-LR configs — one of the reasons ASHA's grace period exists (chapter 6).
