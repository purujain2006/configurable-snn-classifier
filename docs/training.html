Follow one gesture clip through the machinery: millions of events → T binary frames → spikes → a class prediction — including why every batch runs extra empty timesteps, and the mid-run moment the network is swapped onto the chip's integer grid.

5.1The dataset: 1,342 clips of people waving

29 subjects · 11 gestures · 3 lighting conditions · one 128×128 event camera.

raw recording
A long list of events (x, y, polarity, timestamp) — where, which direction brightness changed (ON/OFF → the 2 channels), when (microsecond resolution).
frame mode
SpikingJelly's DVS128Gesture chops each clip into T slices and rasterizes each by counting events per pixel.
split_by="number"
Each slice holds the same number of events — fast motion gets thin time slices, slow motion thick ones.
result per clip
A tensor of shape (T, 2, 128, 128).

Three unglamorous decisions in build_dataloaders worth noticing:

  • The validation split is seeded. torch.manual_seed(1) before the random 15% split — every run, every search trial, judges itself against the same validation set. Comparisons stay apples-to-apples.
  • drop_last only on the training loader. Dropping the ragged final batch is fine for training but on val/test it would silently discard up to N−1 samples "and bias every accuracy number reported."
  • num_workers=0, deliberately. Each search trial is already its own process; DataLoader workers would spawn processes inside processes — "nested multiprocessing like that is broken on Windows and would oversubscribe CPUs across concurrent trials."

Supporting cast (§9)

  • warmup_dataset_cache() — pre-builds the frame cache for every T before parallel trials launch; two trials racing to build the same folder can corrupt it. Detects half-built caches (every class folder must contain samples) and rebuilds them.
  • _quiet_with_heartbeat — swallows SpikingJelly's hundreds of extraction print-lines, emits one calm heartbeat every 20 s, and dumps the full captured log only on failure.
  • validate_data_dir() — replaces the library's cryptic deep-stack FileNotFoundError with a message showing the exact folder layout expected.

5.2Resize + binarize: deliberately lossy, in a chosen direction

128×128×2 = 32,768 input axons. The chip allows 16,383. So: shrink to 64×64 or 32×32, then snap to {0, 1} (spiking input should be spikes, not grays). Two lines, with personality:

Practice2.py · DVSResizeAndBinarize§6
out[t] = F.interpolate(frames[t]..., size=self.size, mode="bilinear", ...)
return (out > 0).float()   # ANY nonzero contribution becomes a full spike
  • This is not average-downsampling: bilinear interpolation of a sparse binary frame produces small fractional values, and > 0 promotes any nonzero contribution back to a full spike.
  • The docstring names it: "effectively OR-pooling — no events are lost, but event density per pixel rises at low resolutions."
  • A deliberate trade: preserve every scrap of sparse signal; accept busier pixels.

With the OR rule, a lone event always survives downsampling (density rises); with averaging it fades to a small gray value that a spiking input can't represent. Same story at 32×32, just stronger.

5.3Reading the answer: rate coding

11 output neurons — one per gesture — each emitting spikes over time. How is that an answer?

  • Rate coding: each output neuron's score = total spikes accumulated ÷ T. Highest rate wins.
  • Training: those 11 rates feed a standard cross-entropy loss, exactly as if they were ordinary scores.
  • The wrinkle (from chapter 2): each layer delays everything by one timestep — so the final frames' evidence is still in flight, mid-network, when the input ends…

5.4The pipeline flush: why the network runs on empty

The fix is forward_over_time(), mirroring the hardware conversion script's measurement exactly:

  • Feed the T input frames…
  • …then keep stepping for flush_steps extra timesteps of all-zero input — one per spiking layer — still accumulating output spikes.
  • Divide by T (not T + flush), so rates stay comparable across network depths.

Turn the flush OFF and add layers: a 6-layer network quietly throws away the last 6 frames — 6/8 of the clip! This bug class is vicious precisely because nothing errors; accuracy is just mysteriously lower on hardware. Modeling the flush during training (every batch, every epoch) makes train-time and chip-time agree.

5.5The training loop, from the inside

One training step, spelled out for readers who haven't seen a PyTorch loop:

  1. Forward. A batch of clips (N, T, 2, H, W) goes through forward_over_time — the full T + flush simulation — yielding 11 firing rates per clip. The membrane states are then reset (functional.reset_net): clips must not leak into each other.
  2. Loss. Cross-entropy between rates and the true gesture, optionally softened by label_smoothing (the true class becomes e.g. 0.85 instead of 1.0 — a mild overconfidence penalty that the winning configs used at ~0.15).
  3. Backward. Backpropagation through time and through spikes: gradients flow back across all T timesteps, crossing every spike via the ATan surrogate (chapter 2) and every quantizer via STE (chapter 4).
  4. Step. Optional gradient clipping, optimizer update, optional per-batch scheduler tick.

After each epoch, evaluate() measures validation accuracy and the best-scoring weights are kept — the final model is the best epoch, not the last one.

Optimizers & schedules

  • build_optimizer offers Adam, AdamW, SGD.
  • The comment that bites people: classic Adam's weight_decay is L2 added to the gradient, tangled with the adaptive step; AdamW decays decoupled.
  • It matters extra here: chapter 4 showed weight decay doubles as a deployment lever (keeps folded weights inside [−1,1]) — so the search gives the two optimizers different decay ranges.
  • build_scheduler shapes the learning rate over epochs:
INTERACTIVE Learning-rate schedule shapes The schedule families build_scheduler constructs (shape sketch). Warmup, when present, is a linear ramp from 10% over the first warmup_epochs, wrapped via SequentialLR.
Why the search's early-stopper must respect schedules: cosine and onecycle do their best work late. Judge a trial at epoch 3 and you systematically favor constant-LR configs — one of the reasons ASHA's grace period exists (chapter 6).
