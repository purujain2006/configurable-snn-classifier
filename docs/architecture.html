The architecture

The configuration specifies layer dimensions and training settings. Before constructing the model, a shared planner derives the dimensions needed by the connection checks. The builder below lets you vary those settings and inspect the resulting network.

3.1The network as configuration

The configuration describes a sequence of convolutional layers that extract image features, followed by a classifier head that turns those features into class scores. The planner calculates the size of every intermediate array before the network is built. Other model families require additional support.

Read the configuration names
N, C, H, W, T
Batch size, input channels, image height, image width, and input timesteps. A batch groups examples for training. It does not multiply the input connections required by one deployed example.
Kernel, stride, padding, dilation
The kernel is the filter window. Stride is the distance between window positions. Padding adds a border around the input. Dilation spaces the filter's sample points apart.
Encoder and head
Here, EncoderSpec names the convolutional feature extractor. It differs from the input encoding on the Training page, which decides how data enters the network over time. The head maps extracted features to class scores.
tau, v_threshold, v_reset
The leak setting, firing threshold, and potential after reset. They are neuron parameters, rather than layer dimensions.
flatten, gap, fc_widths
Flatten keeps every feature position in a vector. Global average pooling (gap) reduces each feature channel to one average. fc_widths lists the sizes of optional hidden fully connected layers before the class outputs.
layers_json
A list of per-layer settings written in JSON, a text format for named values. It overrides the uniform shape settings.
Configuration fields and command-line parsing

If layer dimensions are hardcoded in a model class, changing them requires editing code. This project stores the dimensions in configuration fields so the search can propose a different network for each trial.

Architecture fields describe the network’s shape. Training fields describe how its weights are fitted. Separating them lets the planner check connection limits without constructing an optimizer.

Seven dataclasses hold the shape-determining settings, and an eighth, TrainSpec, holds the optimization recipe. A dataclass is simply a Python structure of named fields with types and defaults.

Reaching the fields from a command line

Each group is exposed as a flag that accepts key=value pairs. One function, fill_from_kv, reads the dataclass's own field list to decide which keys are valid and what type each value should become. Adding a field to a dataclass therefore adds its command-line option without further work.

def fill_from_kv(schema_cls, values: list[str]):
    obj = schema_cls()                                    # start from defaults
    field_types = {f.name: f.type for f in fields(schema_cls)}
    aliases = _FIELD_ALIASES.get(schema_cls.__name__, {})
    for item in values:
        if "=" not in item:
            raise ValueError(f"Expected key=value (e.g. 'N=16'), got: {item!r}")
        key, raw_value = item.split("=", 1)
        if key in aliases:
            key, raw_value = aliases[key](raw_value)
        if key not in field_types:
            raise ValueError(f"Unknown field {key!r}. Valid: {list(field_types)}")
        setattr(obj, key, _cast(raw_value, field_types[key]))
    return obj

An unrecognized key raises with the list of valid field names rather than failing further down the call stack.

norm selects batch normalization (bn), a variant that also normalizes over timesteps (tdbn), or no normalization (none). With no normalization, the model enables convolution bias. dilation spaces filter positions apart to increase the receptive field without adding weights. It remains 1 in this project.

3.2Deriving layer shapes once

How the planner derives shapes

Three parts of the program need the spatial size of every layer: the module that builds the network, the check against the connection limits, and the count of neurons and connections.

The planner computes the layer shapes once. Model construction, feasibility checks, and counts then read the same plan, avoiding separate calculations that could disagree.

plan_network() returns a NetPlan listing every convolution block and linear layer with its input size, output size, channel counts, and cumulative stride, meaning the product of every stride up to that point. The model builder, check_feasibility and count_neurons_and_synapses all take that object as their input.

The per-layer size comes from the standard convolution formula:

out = ⌊( in + 2·padding − dilation·(kernel − 1) − 1 ) / stride⌋ + 1 A 64×64 map through a kernel of 7 at stride 2 with no padding gives ⌊(64 − 7 − 1)/2⌋ + 1 = 29×29. The floor discards positions where the kernel would not fit.

plan_encoder() applies three rules while walking the stack:

  1. Stop shrinking small maps If a feature map has reached 3×3 or smaller, the layer is forced to stride 1 with size-preserving padding whatever the configuration requested. A kernel larger than the remaining map raises InfeasibleConfig with the sizes involved.
  2. Resolve where downsampling comes from A per-layer pool flag takes precedence and produces a stride-1 convolution followed by pooling. Otherwise the global mode decides between a strided convolution and a pooling layer.
  3. Record the result Each block stores its input size, its post-convolution size, which is where the neurons sit, and its post-pooling size, which feeds the next block.

3.3Four different measures of size

Network size can refer to parameters, neurons, or connections. These counts differ because convolutional filters share weights across spatial positions. For a kernel of size k, Cin input channels, Cout output channels, and an H×W output map, the formulas are as follows.

MeasureFormulaMeaning
neuronsCout · H · W Spiking units, one per output position per channel, counted once rather than per timestep.
connectionsneurons · k² · Cin One row per connection the chip has to store, since each output neuron reads its own window.
parametersk² · Cin · Cout Trainable values in PyTorch. One filter is reused at every position, so this is far smaller than the connection count.
SynOps∑ spikes × fan-out Accumulate events actually performed, measured on real data rather than derived from the shape. Covered below.

The fourth measure, which the plan cannot give you

How the counts are measured

Parameter, neuron, and connection counts describe network structure. Computational activity also depends on how many spikes pass through those connections.

A synaptic operation is one addition to a downstream neuron caused by an incoming spike. Summing these operations over a clip estimates activity for that input. The estimate does not include all hardware costs.

SynOpsCounter hooks every spiking layer during evaluation and multiplies the spikes each emits by its fan-out. Every run reports synops_per_sample whether or not the search is asked to act on it.

SynOps = ∑layers ( spikes emitted ) × ( fan-out ) Counted from real spike activity, so it depends on the data as well as the architecture. An ANN of the same shape performs one multiply-accumulate per connection per inference regardless of activity, which is the comparison worth quoting.

SynOps count operations. Energy measurements would also need to account for memory traffic, routing between cores, and static power.

Optimizing for it, or not

SynOps are reported during evaluation. The search offers four ways to use that count when selecting configurations:

Calculate parameters, connections, and activity

A convolution with 32 input channels, 32 output channels, and a 7×7 kernel has 32 × 32 × 7 × 7 = 50,176 weights. If its output is 12×12, it has 32 × 12 × 12 = 4,608 output neurons.

The same weights are applied at 144 spatial positions. That gives 50,176 × 144 = 7,225,344 connections in the expanded representation. Parameters count the reusable filter values. Connections count all the places those values are used.

Neither count specifies how many additions occur during a clip. A source neuron that stays silent triggers no downstream additions. A neuron that spikes repeatedly can activate its outgoing connections repeatedly. SynOps therefore depend on both the wiring and the input-driven spike activity.

For the classifier head, flattening a 32×12×12 feature map produces 4,608 inputs per class neuron. Global average pooling first reduces it to 32 channel averages. This reduces fan-in, but removes the spatial position of features. The interactive builder shows how each choice changes the counts.

3.5The classifier head


 After the convolution stack, a block of shape channels × height × width has to become 11 class scores. The two available reductions differ in how much fan-in they demand from the first linear layer, which section 1.3 limits to 8,159. 






flatten


    

  • Unrolls the block into one vector, so 32×12×12 becomes 4,608 features.
    • 

  • Every neuron in the following linear layer then has a fan-in of 4,608.
    • 

  • Flatten retains spatial position. The leading candidates in the reported search used this head, although that observation does not isolate its effect.
    • 







gap


    

  • Global average pooling reduces each channel to its mean, so 32×12×12 becomes 32 features.
    • 

  • Fan-in drops to the channel count, and many more configurations pass the feasibility check.
    • 

  • An average is a fixed-weight linear map, so the chip can absorb it into the following layer.
    • 

  • GAP discards spatial position. In the comparison at the first stopping checkpoint, it had lower accuracy. Its performance after full training was not measured.
    • 







 Between the reduction and the classifier the configuration may place hidden linear layers. The 65-trial study described in section 6.6 found that the best configurations used none, so the search now allows at most one. Linear layers are built without bias, since the chip provides no bias term. 






3.6Uniform and per-layer encoders


 EncoderSpec accepts two forms. The uniform form takes a depth, a channel count and a kernel size, and repeats them. The per-layer form takes a JSON list of layer dictionaries and gives each layer its own geometry, including per-layer neuron overrides.

3.7Supported models and extension work
The package does not accept an arbitrary model. Its builder creates a sequential convolutional spiking classifier from the configuration. Changing the dataset or layer widths does not change that underlying model family.


Proposed useCurrent supportWhat a lab member needs to do


Change a convolutional classifierConfigurable depth, per-layer geometry, pooling, neuron settings, and classifier head.Choose settings the planner can express, then check shapes, connection limits, and converted accuracy.


Use another image or event datasetBuilt-in loaders and a custom dataset factory.Return training and test datasets plus image dimensions and class count. Match the input encoding and verify the split and labels.


Load any existing PyTorch modelNo general model-import interface. build_model constructs DVSGesturePuru, the configurable model class retained from the gesture project.Adapt the model to the supported configuration, or implement and test a new builder with planning and conversion support.


Add residual connections, attention, or recurrent graphsThe current sequential planner and conversion path do not represent these graphs.Define graph structure, branch timing and merge behavior, then implement supported operations, cost accounting, and conversion.


Use detection, segmentation, or regressionThe current head, loss, and accuracy evaluation assume classification.Add task-specific outputs, training loss, metrics, and data handling. A dataset loader alone is insufficient.


Target another deviceHardware arithmetic and conversion are specialized to HiAER-Spike.Replace the hardware rules, neuron arithmetic, parameter representation, and exporter. Changing connection limits alone does not retarget the tool.




A staged path to broader model support
The following are proposed extensions, not existing interfaces.
  1. Separate experiments from model construction. Define an adapter that supplies a model, its input contract, state reset, loss, and metrics. Ray and Optuna can then manage experiments for other models even when those models cannot run on HiAER-Spike.
  2. Describe supported operations explicitly. Extend the planner from a layer sequence to a graph. Each operation needs shape rules, connection counts, timing semantics, and a supported conversion. Report unsupported operations before training.
  3. Separate device assumptions. Put limits, number formats, neuron updates, and export behavior behind a hardware interface. A new backend needs its own tests against the target runtime.
  4. Validate each extension with a small model. Compare layer outputs and spike timing before and after transformation, then run the converted model on the target device. Follow with accuracy, latency, and energy measurements on a fixed protocol.
General experiment management is achievable without universal hardware support. For a model whose operations cannot be represented on the chip, possible research directions include replacing unsupported operations or training a supported smaller model to imitate its outputs. Either approach changes the model and requires fresh evaluation.
Implementation anchors: snnsearch/model.py builds the sequential model; planning.py derives its shapes; folding.py and quantize.py transform it; data/base.py defines the dataset interface.
