Chapter 3 · Architecture & Configuration

A network you describe,
not hard-code

Most research code hard-wires its network: three conv layers, 128 channels, take it or leave it. This file instead treats the entire architecture as data — seven small config objects that a human can set from the command line and a hyperparameter search can mutate freely. This chapter shows how a config becomes a plan, a plan becomes a network, and a network becomes an exact bill of materials — then hands you the builder.

3.1Seven dataclasses describe everything

A dataclass is Python's way of saying "a named bundle of typed, defaulted fields". The file defines seven, one per concern — together they are the complete genome of an experiment:

DataclassOwnsExample fields (defaults)
InputSpecWhat goes inC=2 polarity channels, H=W=128 sensor size, T=16 timesteps, resize_to=0 (0 = keep native), batch N=16
ConvLayerSpecOne conv layerout_channels=128, kernel_size=3, stride=2, padding=0, dilation=1, pool=False + optional per-layer tau/v_threshold overrides
EncoderSpecThe conv stackEither uniform (depth=3, channels=128, … — every layer identical) or per-layer via layers_json; plus bias, norm ∈ {none, bn, tdbn}
OutputSpecWhat comes outnum_classes=11 gestures
DownsampleSpecHow maps shrinkmode ∈ {stride, pool}, pool_type ∈ {avg, max}, pool kernel/stride = 2
HeadSpecThe classifierfinal_reduction ∈ {flatten, gap}, fc_widths="512" (comma list; "" = none), dropout_rate=0.5
NeuronSpecThe neuron (ch. 2)neuron_type="LIF", tau=2 (integer!), v_threshold=1.0, trainable_tau/threshold=False

An eighth, TrainSpec, holds the optimization recipe — "everything that affects training but not shape" (optimizer, learning rate, scheduler, epochs, and the quantization-aware-training knobs from chapter 4). Keeping shape-things and training-things separate is what lets the feasibility checker run without caring how you'll train.

Setting fields from the command line

Each group gets a CLI flag taking key=value pairs. A tiny generic function, fill_from_kv, reads a dataclass's own field list to know which keys are legal and what type to cast each value to — so adding a config field automatically adds its CLI support, with no argparse surgery:

python Practice.py summary \
  --input   resize_to=64 T=16 \
  --encoder depth=2 channels=32 kernel_size=7 stride=2 norm=bn \
  --head    fc_widths= dropout_rate=0.28 \
  --neuron  tau=2
Practice2.py · fill_from_kv§1
def fill_from_kv(schema_cls, values: list[str]):
    obj = schema_cls()                                    # start from defaults
    field_types = {f.name: f.type for f in fields(schema_cls)}
    aliases = _FIELD_ALIASES.get(schema_cls.__name__, {}) # e.g. old batchnorm=true still works
    for item in values:
        if "=" not in item:
            raise ValueError(f"Expected key=value (e.g. 'N=16'), got: {item!r}")
        key, raw_value = item.split("=", 1)
        if key in aliases:
            key, raw_value = aliases[key](raw_value)
        if key not in field_types:
            raise ValueError(f"Unknown field {key!r}. Valid: {list(field_types)}")
        setattr(obj, key, _cast(raw_value, field_types[key]))
    return obj

Note the error messages: a typo'd key doesn't crash cryptically — it tells you the valid field names. This file consistently spends effort on failing legibly.

3.2Shape planning: the network on paper, one source of truth

Before any real network is built, plan_network() walks the whole architecture arithmetically: given the input size, what does each layer receive and emit? The core is the standard convolution output-size formula:

out = ⌊( in + 2·padding − dilation·(kernel − 1) − 1 ) / stride⌋ + 1 A 64×64 map through a k=7, s=2, p=0 conv → ⌊(64 − 7 + 0 − 1)/2⌋ + 1 = 29×29. Fractions are floored: pixels that don't fit a full kernel placement are dropped.

Around that formula, plan_encoder() makes three quietly important decisions per layer:

  1. "Still big enough to shrink?" If the map is already ≤ 3×3, the layer is forced to stride 1 with size-preserving padding — no matter what the config asked for. This guard stops a deep config from grinding the image to nothing (and if the kernel outright exceeds the map, planning raises InfeasibleConfig with a precise message).
  2. Where does downsampling come from? Priority order: a per-layer pool=True flag wins (stride-1 conv, then a pooling layer); else global mode="stride" uses the layer's conv stride; else (global pool mode) stride-1 conv + pool. One rule, applied identically everywhere.
  3. Record everything. Each layer's plan stores input size, post-conv size (where the LIF neurons live), post-pool size, channels, and effective stride/padding — a ConvBlockPlan.
📐
Why "one source of truth" is a headline feature

The model builder, the hardware feasibility checker, and the cost model all read this same plan object. The file's comment explains the scar tissue: previously the model and the checker each re-derived shapes with duplicated loops, "which is exactly how the head came to be unchecked" — the checker validated the conv layers and silently ignored the fully-connected head, letting infeasible networks through. Duplicate a computation and the copies will drift; compute it once and disagreement is impossible.

3.4The head: flatten vs. GAP, and why it matters so much

  

    After the conv stack, a 3-D block of spiking activity (channels × height × width) must
    become 11 class scores. Two strategies, both configurable:
  

  

    

      
flatten keep every pixel

      
Unroll the whole block into one long vector. A 32×12×12 output flattens to 4,608 features. The first linear layer then needs 4,608 × width weights — and, critically for chapter 4, every output neuron of that layer has a fan-in of 4,608. Preserves spatial detail ("where did activity happen"), which this gesture task rewards: the file notes every top model used flatten.

    

    

      
gap average each channel

      
Global Average Pooling collapses each channel's H×W map to its single mean — 32×12×12 becomes just 32 numbers. Massively fewer parameters, less overfitting, and tiny fan-in (many more configs pass feasibility). Deployable on-chip because an average is just a fixed-weight linear map. The cost: it discards where, keeping only how much — and on this task that historically cost ~40 accuracy points. Tested and kept as an option; not used by winners.

    

  

  

    Between the reduction and the classifier sit zero or more hidden fully-connected layers
    (fc_widths). The 65-trial analysis found the winners used none at all —
    the conv features were already linearly separable — so the search now caps hidden FC layers
    at one. Each linear layer is built bias=False (the chip's linear maps carry no
    bias field), with dropout before it during training, and — like every layer here — a spiking
    neuron after it.
  






  
3.5The cost model: three different ways to count "size"

  

    "How big is this network?" has three genuinely different answers, and the code refuses to
    conflate them. For a conv layer with kernel k, Cin input channels,
    Cout output channels and an Hout×Wout output map:
  

  

    

      
CountFormula (conv layer)What it measuresWho cares

      
        
neuronsCout · Hout · WoutSpiking LIF units — one per output pixel per channel. Counted once, not per timestep.The chip's neuron budget; energy (each neuron updates T times per sample)

        
connectionsneurons · (k² · Cin)Physical synapses realized on hardware. Each output neuron listens to a k×k×Cin window.The chip's wiring; this is what "10 million synapses" means

        
paramsk² · Cin · Cout (+Cout if bias)Trainable floats in PyTorch. Far smaller than connections because of weight sharing: one k×k filter is reused at every image position.Training, memory, overfitting risk

      
    

  

  

    Weight sharing is the punchline: in the depth-2 winner, conv1 has just 50,176 parameters but
    realizes 7.2 million synapses on chip — the same little filter stamped
    across 144 spatial positions. GPUs exploit the sharing; a neuromorphic chip must physically
    wire every synapse. That's why the hardware's constraint language (fan-in/fan-out) is so
    different from deep learning's usual "parameter count".

3.6Uniform vs. per-layer: two ways to write the same encoder

  

    EncoderSpec accepts two styles. Uniform: give
    depth=3, channels=32, kernel_size=7 and every layer is a copy — simple, and
    what the original code did. Per-layer: hand layers_json a JSON
    list of ConvLayerSpec dicts and each layer gets its own geometry — different
    kernels, channel counts, per-layer pooling, even per-layer neuron overrides
    (tau, v_threshold):
  

  

    
per-layer encoder specwhat the per-layer search emits

    
--encoder layers_json='[
  {"out_channels": 32, "kernel_size": 7, "stride": 2},
  {"out_channels": 64, "kernel_size": 5, "stride": 1, "pool": true},
  {"out_channels": 32, "kernel_size": 5, "stride": 2, "tau": 4, "v_threshold": 0.8}
]'

  

  

    When layers_json is present it wins and the uniform fields are ignored
    for shape. resolve_conv_layers() collapses either style into the same
    list[ConvLayerSpec], so everything downstream — planner, checker, cost model,
    builder — handles exactly one representation. Per-layer neuron overrides are free on the
    chip (it reads a neuron model per neuron anyway), but the code deliberately stops at
    per-layer: per-channel τ/θ were "considered and rejected as too many
    degrees of freedom for this dataset."
